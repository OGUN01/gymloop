## Blocking findings

1. **P1 — actual SQL read shape cannot load member or desk screens (BUY-025).** `supabase/migrations/20261004100000_purchase_requests.sql:2577` and `:2620` return a JSON object `{requests,nextAfter,nextAfterId}`, containing camel-case request detail plus nested snapshot, generated by `app.pay_request_json` at `:1346`. `apps/web/lib/purchase.ts:100` treats that object as an array and calls `rows.map`; its detail loaders at `:140` project snake-case flat fields from a camel-case nested object. `apps/mobile/lib/purchase.ts:46` similarly wraps the complete page object as `requests` and attempts `.at(-1)` on that object. The real responses fail before any successful list/detail view. Normalize the one actual RPC protocol and derive display fields from snapshots; preserve server cursors.

2. **P1 — proof GET protocol is mutually incompatible and does not enforce its issued deadline (BUY-009/018).** SQL `:2849` returns a JSON object with camel-case fields. `apps/web/app/api/purchase-requests/[id]/proof-asset/route.ts:41` requires an array and snake-case fields, hence always refuses. It also destructures `requestId` at `:32` despite the route folder being `[id]`. Independently, SQL `:2888` issues a URL with no expiry token; GET rereads to obtain a newly minted deadline and treats query `e` as optional at `:49`. Repeated GETs would renew authorization indefinitely rather than consume the issued 60-second URL lifetime if shape errors were corrected. Require the original immutable deadline and cap it exactly; do not add the five-second cap extension at `:54`. SQL's anonymous `returns record` evidence helper at `:2790`, selected with `select *` and no column definition list at `:2878`, also needs a concrete named return type before accessing `.id`/`.asset_id`.

3. **P1 — recording and attachment ignore the verifier's/requester's expected revision (BUY-010/012/016).** `attach_payment_proof` declares `p_expected_revision` at SQL `:1931` but never validates it or records it in retry facts (`:1953`). Recording declares it at `:2342` but never validates it or includes it in retry facts (`:2400`). Proof replacement does not change accepted revision (`:2044`). Consequently an old verifier can record the newly replaced proof without ever viewing it, and the same retry key with a changed revision is accepted as equivalent. Bind decisions to the exact viewed proof identity and revision, with server comparison and complete normalized retry facts.

4. **P1 — pre-privilege proof confirmation exposure is not exact asset-to-request authorization; attachment ignores registration linkage (BUY-008/009/010).** `supabase/functions/media/index.ts:248` first searches only the latest default-size page (`p_limit:0` resolves to 20); if the asset is not active, `:267` allows *any* live accepted request on that page to authorize privileged lookup. It does not prove the supplied asset was registered to that request. SQL registration correctly freezes `linked_request_id` at `:753`, but attach's asset check at `:1987` never requires it to equal `p_request_id`. A confirmed candidate registered for request A can therefore be attached for the first time to B. Finalizer's A-liveness check does not repair this B attachment. Use a caller-scoped exact registration/request exposure proof before privileged lookup, and enforce the identical linkage on attach independently.

5. **P1 — private signer does not revalidate after awaits (BUY-001/009, MEDIA amendment).** Edge `proofUrl` at `:278` checks request exposure once, then awaits private metadata and signing and returns without a fresh actor/exposure check. Staff deactivation, member erasure/rebinding, proof replacement, or request cancellation between those awaits can mint a new capability after authorization withdrawal. The general photo branch already repeats checks at `:334–339`; private proof needs equivalent exact actor, request, proof disposition and current exposure revalidation. Confirm's already-confirmed early return at `:273` likewise bypasses current registered-request eligibility after privileged lookup.

6. **P1 — unknown upload outcomes discard retry identity and registration has no replay identity (BUY-016/018/021).** Web `apps/web/lib/media-upload.ts:46` and native `apps/mobile/lib/proof-upload.ts:34` register afresh every call, keep asset id/command key only inside the call, and lose them on PUT/confirm network failure. Their UI callers create a fresh key for the next attempt. SQL registration `:680` accepts no key and `:741` tombstones the previous unconfirmed candidate. Retrying an unknown registration/PUT/attach can consume another registration allowance, replace the wrong candidate, and cannot reconcile the original attach result. Preserve a per-selection upload attempt (original registration identity, asset, PUT and attach facts/key) until a definitive outcome, and implement read-only registration replay without resetting counters/deadlines. Native picker await also has no identity generation check, and native hook has no sign-out/rebinding cleanup or identity-scoped last-good stale state (`apps/mobile/lib/purchase.ts:29–66`).

7. **P1 — advertised verifier and replacement flows are not usable (BUY-010/011/025).** Desk detail `apps/web/app/(console)/purchase-requests/[requestId]/page.tsx:30–46` renders no screenshot viewer or proof-fetch action. `purchase-desk-actions.tsx:71` nevertheless claims the currently viewed screenshot is evidence, and `:79` sends empty `assetId` for rejection, which strict UUID validation always rejects. Web member actions `apps/web/app/member/buy/purchase-actions.tsx:62` and mobile `apps/mobile/app/(member)/buy.tsx:117` offer upload only in `owner_accepted`, so the required replacement in `payment_proof_uploaded` is inaccessible. Native does not reload after a successful upload (`:86`) or offer a detail/proof viewer.

8. **P1 — renewal transport has no representable accepted revision (BUY-012/025).** SQL acceptance writes `accepted_revision=null` for renewals at `:1683`, while `purchaseAcceptRequestSchema` requires a UUID, proof confirm extends it, web upload refuses a missing accepted revision, and desk commands send an empty string. A legitimate held-plan renewal cannot complete the published UI/transport protocol. A contract-defined renewal revision must encode/compare the sold snapshot rather than invent a plan quote UUID.

## Positive source observations and limits

The shared publication pipeline verifies exact registered size/MIME and bounded magic bytes through conditional ranged GET, conditionally copies the source into a fresh published namespace, verifies destination ETag/metadata/signature and uses a credential-only finalizer. Unknown finalizer outcomes retain candidate objects rather than treating timeout as rollback. SQL finalizer preserves immutable publication, rechecks actor and registration metadata, and appends actor-attributed confirmation audit without keys/ETags. Registered request linkage is immutable in the media invariant. These are useful source properties; they do not establish deployed R2 behavior or cure the integration/authorization findings above.
