# Decisions

Append-only ADR log. One decision per entry, with rejected alternatives and why. Update an existing entry rather than duplicating it; delete an entry that turns out to be wrong (with a note on what replaced it, in the entry that replaces it).

The **Open Decisions** section at the bottom is different in kind: these are genuine unknowns intentionally left unresolved, tied to the phase that must resolve them. A future session reaching that phase must make the call deliberately — reading this list first — rather than inventing an answer under deadline pressure or rediscovering the gap mid-build.

## Locked stack (master prompt §4)

**ADR-001 — Monorepo: pnpm + Turborepo.** `apps/web`, `apps/mobile`, `packages/shared`, `packages/db`, `packages/api-client`. Rejected: Nx (heavier, more opinionated than this project needs), Lerna (superseded by pnpm workspaces + Turborepo for this scale), a polyrepo (would fragment the single source-of-truth doc framework across repos).

**ADR-002 — Web: Next.js App Router + React + TypeScript strict + Tailwind, on Vercel.** Rejected: Remix (smaller ecosystem for this team's needs), plain Vite SPA (loses SSR/route handlers needed for the API split in ADR-012), self-hosted Node server (Vercel's India edge presence and zero-ops deploy win for a small team).

**ADR-003 — Mobile: Expo + React Native, New Architecture mandatory, EAS Build + OTA.** Rejected: Flutter (explicitly rejected by the master prompt — different language/ecosystem from the web stack, no code-sharing with `packages/shared`), native iOS/Android (2x the engineering surface for a small team). Version pinning deferred — see ADR-020.

**ADR-004 — Database/Auth: Supabase Postgres, ap-south-1 (Mumbai).** Rejected: **Neon** — no India region (nearest is Singapore/Sydney), and India latency is a stated product requirement (a metro-gate-speed QR check-in cannot round-trip to Singapore). Rejected: self-hosted Postgres (loses Supabase's Auth, RLS tooling, and generated-types workflow that this whole doc framework is built around). Provisioned project: ref `pecxrpskmfeuyzngvewq`, org `gjjnocawiprbwdkktogn` — see `AGENTS.md` for the multi-account trap this created.

**ADR-005 — Tenancy: single database, Row-Level Security, `tenant_id` from a JWT claim.** Rejected: database-per-tenant (operationally heavy at hundreds of small gyms, migrations must run N times), schema-per-tenant (Postgres schema-per-tenant hits connection-pooling and migration-tooling friction at this scale). RLS with an indexed, JWT-sourced tenant claim is the standard Supabase multi-tenancy pattern and is what gates 6-8 (`docs/gates.md`) exist to verify.

**ADR-006 — Object storage: Cloudflare R2 + Cloudflare Images, short-lived presigned URLs.** Rejected: S3 directly (R2 has zero egress fees, which matters for member photo/video-heavy usage at scale), public bucket URLs (presigned URLs enforce the authorization check server-side before any access).

**ADR-007 — Edge/security: Cloudflare DNS, CDN, WAF, Turnstile.** Rejected: reCAPTCHA (Turnstile is privacy-friendlier and free at this scale, and the team already standardized on Cloudflare for DNS/CDN).

**ADR-008 — Payments: Razorpay, each gym connects its own account.** Rejected: a platform-custodial payment model where Gymloop holds member money (would require a payment aggregator license in India — out of scope for a software SaaS); Stripe (weak UPI/domestic-India rail support compared to Razorpay); PayU/Instamojo (Razorpay has the strongest Indian developer ecosystem and is what competitors' integrations are benchmarked against — see `docs/architecture.md`'s Quality-bars section on why competitors are the feature reference and never the bar; this is an infra choice, not the loop itself).

**ADR-009 — Jobs: `pg_cron` for scheduled scans, `pgmq`/Supabase Queues for dispatch with retry + dead-letter.** Rejected: an external queue (SQS, BullMQ+Redis) — adds an operational dependency outside Supabase for a workload (daily scans, notification dispatch) that Postgres-native tooling handles at this scale, and keeps everything in one place for the `tenant_id`-carrying structured logs (ADR-010).

**ADR-010 — Observability: Sentry (web, mobile, edge) + structured JSON logs carrying `tenant_id`.** Rejected: a self-hosted error tracker (operational overhead not justified pre-revenue); logs without a tenant dimension (would make gate 28's per-tenant incident triage impossible).

**ADR-011 — i18n: English + Hindi from day one.** Not deferred to a later phase — Indian gym staff and members routinely mix languages, and retrofitting i18n into components built English-only is expensive. Rejected: English-only for v1 with i18n "added later" (the standard version of this decision, and the reason so many Indian SaaS products never ship Hindi at all); a third language in v1 (no evidence of demand, and each one multiplies copy review).

**ADR-012 — API architecture: mutations via Next.js Route Handlers (zod + typed error envelope); reads direct via supabase-js + RLS; Supabase Edge Functions only for Razorpay webhooks and cron.** Rejected: GraphQL (adds a resolver layer with no clear win over direct RLS reads for this data shape); tRPC (couples client/server in a way that complicates the shared `packages/api-client` used by both web and mobile); Edge Functions for all backend logic (Vercel Route Handlers are colocated with the web app and simpler to deploy; Edge Functions are reserved for the two things that must sit next to the database regardless of Vercel's availability — webhooks and cron).

**ADR-013 — Explicitly rejected, do not reconsider:** Cloudflare Workers as the backend, Cloudflare D1 as the database, Neon, Flutter, no-code builders.

## Locked product decisions (master prompt §5)

**ADR-014 — Distribution: one member app for all gyms, joined by invite QR / 6-char gym code / automatic phone-number match against an imported roster.** Phone-number auto-match is the path that actually works for non-technical members and gets the UX investment. In-app branding is gym logo + one accent colour + gym name; a member in two gyms gets a header switcher. Rejected: a white-label app build per gym (an App Store review and an OTA fan-out per gym, defeating the one-shared-app distribution); gym-code-only onboarding with no phone-roster auto-match (the code path is the one non-technical members fail at).

**ADR-015 — Payments: per-gym Razorpay account, platform takes no cut, offline-first is a first-class state.** Most early gyms will have no gateway connected — that state must be fully functional (cash/UPI/card recorded by front desk, with attribution, receipts, and a working renewal pipeline), not a degraded fallback. Onboarding verifies both API keys and the webhook secret with a real ₹1 test payment before go-live. Rejected: platform-custodial payments where Gymloop holds member money (already rejected in ADR-008 — needs an aggregator licence, and revenue is subscription-only); a gateway-required launch that treats gyms without Razorpay as a degraded mode (most early gyms are exactly that state, so it must be the fully functional default).

**ADR-016 — Messaging v1: push notifications (Expo + FCM/APNs) + click-to-WhatsApp (`wa.me` deep links).** No SMS, no DLT registration in v1. Written as a provider interface with a per-gym credit wallet from day one, because Indian competitors (GymForce, Akton, GymFito, AdviceFit) already ship WhatsApp Business API — see "Market context" at the end of this file; this is table stakes arriving in Phase 1.5, not a nice-to-have. Rejected for v1: WhatsApp Business API directly (cost and Meta approval lead time not justified before product-market fit), SMS/DLT (India's DLT registration overhead is significant for a pre-revenue product).

**ADR-017 — Commercial: hosted SaaS, tiers by active-member count (~₹1,499/₹2,999/₹4,999/month), 14-day full-feature trial, manual super-admin activation at launch.** Rejected: matching competitors' ~₹89/month pricing — beating rock-bottom Indian gym software on price proves nothing; the product differentiates on the retention loop (no-show red list, follow-up outcomes, measurable recovery), not on being cheaper. In-app platform billing of gyms is Phase 1.5; v1 activation is manual.

## This session's decisions (Phase 0)

**ADR-018 — TypeScript pinned to 6.0.3, not the newer 7.0.2.** `typescript-eslint@8.69.0`'s peer range is `>=4.8.4 <6.1.0`; TS 7 breaks it. Verified via `npm view` before pinning. Fall back to `5.9.3` if a future Phase's type-generation surfaces a TS 6-specific issue — record that as a new ADR entry if it happens, don't silently downgrade.

**ADR-019 — `apps/mobile` and `packages/api-client` deferred rather than stubbed.** Confirmed with the user. An empty package trips the `knip` unused-export gate this same change arms; mobile UI is explicitly Phase 7 work in the build order. Rejected: scaffolding all five `apps/*`/`packages/*` per §4's literal layout now — contradicts §14's "no scaffolding for later." `docs/architecture.md` documents the full five-package target layout so a future session reads the gap as a decision, not a bug.

**ADR-020 — Expo/React Native version deliberately left unpinned until Phase 7.** §4's SDK 56/RN 0.85 pin was already one SDK behind current (57.0.20/RN 0.87.1) when this session checked. Pinning "whatever's current now" would only repeat that staleness by Phase 7. The version is chosen when Phase 7 starts, against whatever is current then.

**ADR-021 — Canonical status vocabularies (`docs/data-model.md`) are Postgres enums generated into `packages/db/types/database.ts`, never hand-written TypeScript constants.** The master prompt's own truth chain is Postgres enum → `supabase gen types` → generated TS types → derived zod schemas (§10). Writing them into `packages/shared/src/config/constants.ts` now would create a second source Phase 1 would then have to reconcile or delete.

**ADR-022 — `packages/shared` is kept platform-free from day 0**: its `tsconfig.json` sets `"lib": ["ES2022"]` (no DOM) and `"types": ["node"]` explicitly (TS 6's automatic `@types` discovery did not pick up `@types/node` in this workspace layout — verified by a failing typecheck before the explicit `types` array was added); a `dependency-cruiser` rule forbids importing `next/*`, `react-dom`, or `node:*` from it. It is consumed by web, mobile, and Edge Functions — a platform leak here becomes a Phase 7 blocker discovered at the worst time.

**ADR-022a — The `next`/`react-dom` portability rules match `couldNotResolve: true`, not a path against their resolved `node_modules` location.** Found by actually attempting the violation the rule was meant to catch: under pnpm's strict per-package `node_modules`, `next` and `react-dom` are not resolvable at all from `packages/shared` (it never lists them as dependencies) — a rule matching `to: { path: "node_modules/next/" }` silently never fires, because there is no resolved path for it to match. `couldNotResolve: true` catches exactly that unresolvable case and is strictly more general: it forbids *any* platform-specific package sneaking into `packages/shared` later, not only the two named at the time this rule was written. Lesson for writing any future dependency-cruiser rule in a pnpm workspace: verify a "forbid importing X" rule by actually importing X and checking the tool reports a violation — don't trust that a path-based rule fires just because it typechecks.

**ADR-023 — `packages/shared/src/config/env.ts` validates lazily (on first property access, cached) rather than eagerly at module load.** An eager `zod.parse()` throws during `next build` in CI, where no env vars are set, turning the build gate red on missing secrets rather than on broken code. Rejected: seeding CI with placeholder secret values — puts fake secrets in a checked-in workflow file and trains future sessions that a green build implies a valid environment. A documented consequence: `clientEnv()`/`env()` require a real `process.env` object (server components, Route Handlers, Edge Functions, Node scripts) — a `"use client"` component must read `process.env.NEXT_PUBLIC_X` as a literal expression directly (Next.js's client-bundle replacement only rewrites literal member expressions), not call these functions; read server-side and pass the value down as a prop.

**ADR-024 — The schema-drift CI gate compares `supabase gen types --linked` (against Supabase Cloud) against the committed `packages/db/types/database.ts`. Reversed from an earlier `--local`/Docker design — see the history below.**

**History, because the reasoning that got here matters for whoever touches this next.** The gate was first built comparing `--local` (a disposable Docker Postgres via `supabase start`) against committed, reasoning that it would be hermetic and immune to a transient network failure reaching Cloud. That design cost more than it saved, discovered across two real CI runs, not assumed:
1. First run: CI was pinned to Supabase CLI `2.116.0` while the committed file was generated locally with `2.110.0` — a real mismatch, fixed by re-pinning.
2. Second run, identical diff, even with both sides confirmed on the same CLI version: `--local` and `--linked` turned out to emit genuinely different template output for the identical schema (an extra `__InternalSupabase` block, different conditional-type parenthesization) — a structural property of the two generation paths, unrelated to version.
3. On top of both bugs, Docker added ~5-6 minutes of image-pull time to every CI run, for a job whose entire purpose is a text diff.

The deeper problem the two bugs exposed: the app's real database is **always** Supabase Cloud — `--local`'s disposable stack only *approximates* it, and turned out not to even do that reliably. `--linked` checks the invariant that actually matters (does the committed file match what's really deployed) directly, needs no Docker, and removes the whole `--local`-vs-`--linked` template-mismatch bug class permanently, since there's now only one generation path. The accepted risk — a transient network failure to Supabase's API causing a spurious red — is smaller than the bug class and slowdown it replaces, and is what a re-run is for.

`SUPABASE_ACCESS_TOKEN` is a required repo secret for this gate (previously only needed starting Phase 1's `supabase db push`). **It is set**, and gate 10 is proven: on the gate-proof PR the job authenticated, generated from Cloud, and caught exactly the hand-edit (`-export type GateProofBogusHandEdit = true;`), while passing on `main` in the same round — so it discriminates rather than failing always. A human must create it (the CLI's stored token lives in the OS credential manager and isn't extractable by an agent) from the account owning `pecxrpskmfeuyzngvewq` / org `gjjnocawiprbwdkktogn`, then `gh secret set SUPABASE_ACCESS_TOKEN -R OGUN01/gymloop`.

**The current token must be rotated** — see `docs/security.md`, "Credential rotation".

*This paragraph previously asserted the token was NOT set and the gate jammed. It was left stale after the token was added, and a second verification pass caught it — the same overclaim class the first audit found, in the same file. If you change the state of a credential or a gate, grep for every doc that describes that state before you consider the change done.* `db.yml` uses `supabase gen types --project-id pecxrpskmfeuyzngvewq`, not `--linked` — a fresh CI checkout has no prior `supabase link` state (`supabase/.temp/` is gitignored, a local session artifact) and `--linked` would fail with "Cannot find project ref" without it; `--project-id` needs no link step and was verified byte-identical to `--linked`'s output against the same project before switching.

**Docker is now used nowhere.** This paragraph previously said Docker survived in the `pgtap` job for an isolated, disposable database. ADR-030 removed that too: pgTAP runs against the Cloud project with every test file wrapped `BEGIN … ROLLBACK`, after CI applies migrations on merge. There is no `supabase start` anywhere in CI or in the documented local workflow.

**ADR-025 — The real OpenSpec CLI is `@fission-ai/openspec`, not the package published as `openspec` on npm.** The bare `openspec` name is a dead 2022 package (`openspecio`, last published 2022-05-12) unrelated to the actively maintained tool this project uses.

**ADR-026 — `no-magic-numbers`'s `ignore` list includes `[0, 1, -1]`, discovered via a real lint failure, not decided upfront.** Every `z.string().min(1)` in `env.ts` tripped the rule as originally scoped (`ignoreArrayIndexes`/`ignoreDefaultValues`/`ignoreEnums` don't cover an arbitrary call argument), and zod has no `.nonempty()` method for strings (confirmed against current docs) — there is no numeric-literal-free way to express "non-empty string" in zod. Confirmed with the user rather than silently widened, per the standing instruction to treat any apparent need for a rule exception as a finding, not a line to quietly add.

**ADR-027 — `scripts/**` is entirely exempt from the test-immutability rule.** Discovered by actually running `check-test-immutability.mjs` against this repo's own commit that added it — the rule flagged its own authoring commit (a script and its test, added together) as a violation. The rule's actual purpose (master prompt §9) is to stop an implementer quietly loosening a *product* test derived from an approved EARS spec — CI/build tooling under `scripts/` never goes through that pipeline, so a script and its own test belong in one commit. Rejected: adding a `spec:` prefix to qualify — that prefix means "human-approved specification change," which this isn't.

**ADR-028 — `turbo.json`'s `lint`, `typecheck`, and `test` tasks declare no `dependsOn`, so every gate runs independently.** They originally each declared `dependsOn: ["^build"]`. A fresh-context critic auditing the gate-proof PR caught what that actually did: when the deliberate type error broke `build`, turbo aborted the whole task graph *before ESLint ever executed* — the `lint` job went red having run zero lint rules, and the `test` job went red while all 4 tests actually passed. The `no-magic-numbers` proof was therefore worthless, and a real type error would mask every lint finding in normal development too. This directly contradicted the design principle stated in `db.yml`'s own comment ("every gate is its own parallel job — a bad commit must show every gate it breaks at once, not stop at the first failure"): running the gates as parallel CI *jobs* achieves nothing if turbo serialises them again underneath. The dependency was pointless as well as harmful — `packages/shared` and `packages/db` are consumed as TypeScript source (`main` points at `src/index.ts` / `types/database.ts`), their "build" scripts are bare `tsc --noEmit` producing no artifacts at all, and turbo had been signalling exactly that with `no output files found for task @gymloop/db#build` on every run. Verified after the fix: `lint` now catches the magic number, `test` passes 4/4 independently, `typecheck` still fails on the real type error.

**ADR-029 — `AGENTS.md` deliberately omits the master prompt §10 instruction to "archive, clear and restart" at ~70% context.** §10 mandates that line; `AGENTS.md` says the opposite ("you have a large context window; don't stop or suggest a new session on account of context limits"). Recorded as an ADR because a blind critic correctly flagged it as an undocumented spec deviation. Reason: that threshold was calibrated for smaller context windows, and surfacing context countdowns to a model with a 1M-token window triggers a documented failure mode where it truncates its own work or proposes a handoff mid-task. Rejected: keeping the line as written (it would have caused exactly that behaviour during Phase 0, which ran long); deleting it silently (which is what happened first, and is why this ADR exists).

**ADR-030 — Database strategy for Phase 1: one Supabase Cloud project (`pecxrpskmfeuyzngvewq`), no Docker, no branching. Resolves OPEN-005.** Decided by the product owner. The three conditions that make a single shared database safe are rules, not conventions:

1. **Every pgTAP test file is wrapped `BEGIN … ROLLBACK`.** A test that commits is a bug. Enforced by `scripts/check-pgtap-rollback.mjs` (the `pgtap-rollback` job in `db.yml`), which fails on any `supabase/tests/**/*.sql` whose first statement is not `BEGIN` or whose last is not `ROLLBACK`.
2. **No session and no cluster agent pushes migrations to Cloud, ever.** Migrations are written in-branch and applied only by the `migrate` job in `db.yml`, on merge to `main`, in merge order — `supabase db push --linked`, with `--dry-run` on a pull request. `AGENTS.md` rule #7 stays literally true. The `schema-drift` and `pgtap` jobs run after `migrate`; on a PR that changes `supabase/migrations` both skip with a notice and run on the post-merge push of `main`, because Cloud cannot reflect an unmerged migration.
3. **The full pgTAP suite runs after each cluster merges, never concurrently.** The workflow's `concurrency` group serialises `main` runs.

Needs no database password: with `SUPABASE_ACCESS_TOKEN` set, the CLI mints a temporary login role through the Management API (`POST /v1/projects/{ref}/cli/login-role`) for `link`, `db push` and `test db --linked` — proven from CI on the throwaway PR #3, which linked and dry-ran a no-op migration with the password variable empty. Rejected: option 2 of OPEN-005, a hermetic Docker database from committed migrations — ADR-024 already recorded that `--local` and `--linked` emit different output and cost minutes per run; option 3, a split hermetic check plus a Cloud monitor — two jobs and a Docker dependency for a Phase with no real data yet; Supabase branching — a second environment to keep consistent before there is anything to protect. **Revisit, deliberately, not now:** see OPEN-006 and OPEN-007.

## Phase 1 decisions (data model)

Taken during the overnight Phase 1 run with the product owner asleep and the run authorised end to end. Each is the safest default the orchestrator could pick against the docs as written; each is listed again under "Open decisions" so the owner can confirm or reverse it deliberately rather than inheriting it silently.

**ADR-031 — The `app_role` Postgres enum is the one role vocabulary. `ROLES` and `Role` in `packages/shared/src/config/constants.ts` are retired.** Phase 1 creates `app_role` as a Postgres enum because `staff.role`, `organization_settings.pause_approver_role`, `platform_users.role` and `audit_log.actor_role` are all columns that need it, and a column's domain is a database type. Keeping the TypeScript array as well would leave two role vocabularies that can drift — exactly what `docs/registry.md` exists to prevent, and the same failure mode ADR-021 rejected for the status vocabularies. Note the tension this resolves: `docs/architecture.md` explicitly listed "the fixed role list" as belonging in `constants.ts` *outside* the truth chain, written before it was known that roles would be a column type. That sentence is updated in the same change rather than left to contradict this. Rejected: keeping both and calling `constants.ts` "the UI's copy" (a second source is a second source); leaving `staff.role` as `text` with a check constraint so `ROLES` could stay canonical (loses the generated TypeScript union that is the entire point of the truth chain).

**ADR-032 — The tenant claim is `tenant_id` and the role claim is `app_role`; both are read through two `stable` functions in a private `app` schema, never inline in a policy and never via a subquery.** Naming the claims and the accessors once, before six agents write policies in parallel, is what stops the fan-out producing three dialects of the same predicate. The functions live in `app` rather than `public` because a function in `public` is exposed by PostgREST as an RPC endpoint and appears in `packages/db/types/database.ts`, widening both the API surface and the drift check for no gain; `app` is not in `config.toml`'s exposed `schemas`, so it is neither. They are `security invoker`, not `security definer`: they only read the JWT and never touch a table, so definer rights would buy nothing and hand a future caller an RLS bypass. A missing or empty `tenant_id` claim yields `NULL`, so the policy predicate is `NULL` and matches no rows — an unauthenticated or hook-less token sees nothing, without raising. A *malformed* claim (present but not a uuid) raises on the cast, which is the correct loud failure. Rejected: `auth.jwt() ->> 'tenant_id'` written inline in every policy (unreviewable at 30 tables, and impossible to change centrally when Phase 2's hook lands); a `user_metadata` claim (user-editable in Supabase, so unsafe for any authorization decision); a per-row subquery against a membership table (gate 8 forbids it, and it is the documented source of cross-tenant leaks in Supabase RLS setups).

**ADR-033 — Exactly two tables sit outside tenant scoping, and both are platform-owned.** `platform_users` carries no `tenant_id` at all: a super admin belongs to the platform, not to a gym, and inventing a nullable tenant column for it would make gate 6's "every table has a tenant_id" true in letter while meaning nothing. `audit_log.tenant_id` is nullable because a platform-level event (a role change among platform users) genuinely has no tenant; a null-tenant row is visible only to the platform policy. Both are named exhaustively in `docs/data-model.md`'s contract, and a pgTAP meta-test asserts that no *third* table is missing tenant scoping — so the exemption is a closed list, not a precedent. Rejected: giving `platform_users` a `tenant_id` pointing at a synthetic "platform organization" row (a fake tenant that every cross-tenant test would then have to special-case).

**ADR-034 — `supabase/seed.sql` is applied by a manually dispatched CI workflow (`.github/workflows/seed.yml`), via `supabase db query --linked -f`.** The one command is `gh workflow run seed.yml -R OGUN01/gymloop`. A seed is data, not schema, so it does not belong in the forward-only migration stream that `db.yml` applies on every merge — a demo gym must not be re-created on Cloud every time an unrelated migration lands. It cannot be run from a session either: sessions hold no database credentials, and ADR-030's rule is that CI owns writes to Cloud. `workflow_dispatch` keeps both true, makes every seeding an audited run with a log, and shares `db.yml`'s `concurrency` group so a seed can never run while a migration is applying. The file is idempotent, so a second dispatch converges rather than duplicating. Rejected: `supabase db push --include-seed` (would seed on every merge); a seed migration (forward-only means it could never be corrected, and it would run against a production project); documenting a local `supabase db query` command as the answer (works, but puts a Cloud write back in a session's hands, which is the one thing ADR-030 exists to prevent — it stays in `README.md` only as the description of what the workflow does).

**ADR-035 — Primary keys are `uuid default gen_random_uuid()`.** The Supabase best-practice guide prefers `bigint generated always as identity` for index locality, and this is a deliberate departure from it. Sequential ids in a multi-tenant product leak information across tenants — row counts, growth rate, and neighbouring gyms' volume — through any surface that shows an id, and ids here appear in URLs, QR payloads and receipt references. Postgres 17 has no built-in `uuidv7()` and `pg_uuidv7` is not available on this project (verified against `pg_available_extensions`), so time-ordered uuids are not an option; random v4 and its B-tree fragmentation is the cost of the property that matters. Revisit if a table ever reaches the scale where insert locality dominates — at 100 gyms × 500 members it does not.

**ADR-036 — DPD-007 is split: the per-table retention policy is written now, in Phase 1; the breach-notification runbook is deferred to Phase 8.** `docs/security.md` required whoever planned Phase 1 to make this call explicitly rather than assume it away. The retention policy is a property *of the schema* — it can only be written once the tables exist, and it is cheapest to write while the table list is in front of you, so it lands in `docs/security.md` in this change. The breach-notification runbook is an operational document about people and timelines, not about tables; nothing in Phase 1 makes it easier or harder to write, and Phase 8's launch checklist is where the rest of the pre-launch operational work already lives. Rejected: deferring both (the retention policy would then be written by a session that has to re-derive the whole table list); doing both now (Phase 1 has no incident-response contacts, escalation path or notification channel to write down, so the runbook would be a placeholder pretending to be a deliverable).

**ADR-037 — Table privileges are revoked and re-granted per table, in the same migration that creates the table; `delete` and `truncate` go to nobody, and `anon` gets nothing anywhere.** Row-Level Security is not a privilege system, and on this project the distinction is not theoretical. Verified by reading `pg_default_acl` on `pecxrpskmfeuyzngvewq` directly: for tables created by `postgres` in schema `public`, the default ACL is `{postgres=arwdDxtm/postgres,anon=arwdDxtm/postgres,authenticated=arwdDxtm/postgres,service_role=arwdDxtm/postgres}` — every privilege including `d` (delete) and `D` (truncate), to `anon` and `authenticated`, on every table, automatically. `truncate` is not filtered by RLS at all, so a table with perfect policies and default privileges can be emptied by any signed-in user. Hence, per table and written out in full: `revoke all … from anon, authenticated;` then `grant select, insert, update … to authenticated;` (or `select, insert` on an append-only table). Rejected: `alter default privileges in schema public revoke all on tables from anon, authenticated` as *the* mechanism — it silently changes every future object created by any tool including Studio, it is invisible where a reader audits a table, and it does not cover objects created by another role; it may later be added as a second belt but may not replace the first. Rejected: the `on all tables in schema public` form of `grant` — a later cluster running it re-grants across every earlier cluster's tables. Rejected: `force row level security` — it buys nothing here and it misleads. `force` only ever changes what the *table owner* sees; the roles that carry a user request are `authenticated` and `anon`, and both are already fully subject to every policy. Isolation is proven for `authenticated`, and that is what gate 7's suite asserts.

*Correction, recorded rather than quietly fixed (found by the Phase 1 blind critic on the tenancy migration).* This entry, `docs/data-model.md` and `design.md` all previously rejected `force` on the grounds that it "would subject `postgres` to its own policies, so the seed would write nothing". **That is factually wrong on this project.** `postgres` here holds `rolbypassrls = true` — verified with `select rolname, rolbypassrls from pg_roles` (`postgres`, `service_role`, `supabase_admin` true; `authenticated`, `anon` false) — and a `BYPASSRLS` role bypasses row security unconditionally, which `FORCE ROW LEVEL SECURITY` does not override. So `force` would not have broken the seed or the pgTAP fixtures. The decision is unchanged; only its stated reason was wrong, and it was wrong in three documents at once because it was reasoned about rather than run. The `pg_default_acl` half of this ADR *was* run against Cloud, and it held.

**ADR-038 — Tests and implementation are two commits in one push, and the red pgTAP run is bought once rather than seven times.** `AGENTS.md` rule 10 requires the test committed before the implementation that answers it, and `check-test-immutability` enforces it **per commit** — so two commits in a single push satisfy it exactly as two pushes would. What a single push gives up is a CI run observing the tests red. Under the owner's trunk-only decision there is no PR to absorb that run: on `main`, `db.yml` skips nothing, so a tests-only push applies no migration and runs pgTAP against tables that do not exist, leaving `main` red until the next push. Phase 0's hardest-won lesson is that a green tick is not evidence and a red one is not either until you read why — so the `tenancy` contract cluster pushes its tests alone first and that red run is recorded as proof the pgTAP runner discriminates rather than passing vacuously. The six fan-out clusters then push both commits together, and `main` stays green. Rejected: seven red runs on `main` (a deliberately broken trunk, on a repo whose rule is that `main` stays green, to re-prove the same one thing six more times); rejected: no red run at all (then nothing distinguishes a working pgTAP job from one that silently runs zero assertions, which is precisely the jam Phase 0 shipped twice).

**ADR-039 — A calendar-day column default is `(now() at time zone 'Asia/Kolkata')::date`, never `current_date`.** Found by the contract migration's implementer while transcribing `members.joined_on date =current_date`, and it is a real bug in the contract rather than a style preference. `current_date` evaluates in the **session** timezone; every Supabase connection is UTC. So for a gym in IST, any row inserted between 00:00 and 05:30 local time gets *yesterday's* date — and 05:00 is real gym traffic, not a theoretical edge. MNY-004 is explicit that a calendar day the gym reasons about is evaluated in the gym's timezone. Two columns are affected, `members.joined_on` and `no_show_cases.opened_on`, in two different clusters, which is why this is a contract change rather than a one-line patch. Rejected: dropping the default entirely and requiring the application to supply the date — correct in principle, but Phase 1 has no application layer, the seed would have to supply it everywhere, and a column with no default is a nullability question the table list has already answered. Rejected: a default that reads `organizations.timezone` — a column default cannot reference another row, and a trigger to do it would be behaviour in the database, which Phase 1 does not own. The literal `'Asia/Kolkata'` knowingly duplicates `DEFAULT_TIMEZONE` in `packages/shared/src/config/constants.ts`; a migration cannot import a TypeScript constant, so the duplication is recorded in the contract as the second place to change rather than pretended away. **Known limit:** the default is right for every v1 gym and wrong for a gym outside IST, which Phase 3 must handle by supplying the gym-local date explicitly.

**ADR-040 — The check-constraint rule word is fixed, because it was the one thing in the naming table left to taste.** The contract gave the pattern `<table>_<rule>_chk` and never said what `<rule>` is; its own two examples disagreed (`organizations_gym_code_format_chk` uses `_format_`, `<table>_currency_chk` does not). Six agents each naming roughly fifteen checks with no rule would have produced six dialects — exactly the failure the Conventions section exists to prevent, and the reconciliation would have been ninety constraint names after the fact. Now: a regex check is `<table>_<column>_format_chk`, a range or bound is `<table>_<column>_chk`, and a multi-column rule is `<table>_<phrase>_chk`. Raised by the contract migration's implementer as the highest-risk under-specification in the document before merge 2, which is when it would have started costing.

**ADR-041 — The currency check is `<table>_currency_format_chk`, and ADR-040's rule word wins over a literal template that contradicts it.** `docs/data-model.md` fixed the naming rule in one section (a regex check is `<table>_<column>_format_chk`, ADR-040) and, two sections later, still handed every cluster the literal template `constraint <table>_currency_chk`. `currency ~ '^[A-Z]{3}$'` is a regex, so the two lines could not both be followed. The `tenancy` implementer transcribed the literal template — correctly, since that is what the contract said — and the blind critic caught the contradiction before the other eleven `currency` columns landed in merges 2 through 7. The general rule wins: renaming one constraint now is a `sed`, renaming twelve after the fact is the ninety-name reconciliation ADR-040 exists to prevent. `docs/data-model.md` is corrected in the same change. Rejected: keeping `<table>_currency_chk` and adding it to ADR-040 as a named exception — an exception in the one convention that exists to remove taste is how the next six exceptions get argued for.

**ADR-042 — A migration is validated before it is pushed by replaying it inside `begin … rollback` against Cloud, and it is still applied only by CI.** Hard rule 7 and ADR-030 say CI applies migrations; they do not say a migration must reach `main` unexecuted. Seven migrations landing serially, each verified only by a CI round trip, means every syntax slip costs a red `main` and a fix-forward commit. Verified against the project before relying on it: `supabase db query --linked` connects as `postgres` with `rolbypassrls = true` and `rolsuper = false` — the same session shape the pgTAP job runs in — and it honours an explicit transaction: `begin; create table public.__probe_rollback(x int); rollback;` left `information_schema.tables` with zero rows for that name. So the orchestrator concatenates `begin;` + the migration + the cluster's pgTAP file and runs the whole thing through `db query --linked`; the test file's own trailing `rollback` unwinds the migration with it, and the schema is re-checked empty afterwards. Nothing is committed, which is precisely the guarantee ADR-030 already leans on for the entire pgTAP suite running against this same shared project. Rejected: pushing and letting CI find it (a red `main` per typo, and ADR-038 spends the one deliberate red run on something that actually proves a property); rejected: `supabase db push` locally (that *is* an apply, and it is the rule with the second-worst blast radius here); rejected: Docker and a local instance (ADR-030, and the daemon is not running on this machine — verified). **Limit, stated so it is not overclaimed:** this proves the migration executes and the assertions pass; it does not prove `supabase db push` will sequence the files the same way, so the CI `migrate` log stays the evidence of record. Available to the orchestrator, not to cluster agents — their brief forbids every mutating `db query`, and the distinction between "mutating" and "rolled back" is exactly the judgement call that should not be fanned out six ways.

**ADR-043 — A holdout pgTAP file that references a not-yet-merged cluster is parked in `supabase/tests-staged/`, and moved back unchanged when its migration lands.** The holdout repo's own `supabase/tests/README.md` already states the rule — "a file may only reference schema objects that have already merged. A holdout file pushed ahead of the migration it tests turns `main` red for a reason that is not a defect" — and two files broke it: the blind holdout authors for `attendance` and `comms` pushed before the `tenancy` migration had even landed. Left in place they would have held `gymloop`'s `pgtap` job red through four unrelated merges, which destroys the one property the serial landing exists to give: *this* cluster is green before the next one starts. `supabase/tests-staged/` is looked at by neither `supabase test db` (which is passed `supabase/tests` explicitly) nor `check-pgtap-rollback` (which globs `supabase/tests/*.sql` through `git ls-files`), so a parked file runs nowhere and is checked nowhere until it is moved back. **The move was made through GitHub's git-data API by blob sha — a tree entry deleted at one path and re-created at another with the identical sha — so the orchestrator never read, downloaded or rendered the contents**, which is the property AGENTS.md rule 10 actually protects. Rejected: leaving them and reading the `pgtap` log per merge to decide whether the red was "the expected red" — that is exactly the jammed-gate failure `docs/gates.md` records from Phase 0, where a job is red for a reason nobody checks and a real failure hides inside it. Rejected: deleting them and asking the authors to re-push later — a blind author's output should not be re-derived, and a blob sha round-trips it byte-identically.

**ADR-044 — The orchestrator repaired two mechanical defects in the visible pgTAP suite before it was ever committed, and this does not weaken hard rule 10.** The interrupted run left nineteen visible test files uncommitted. Replaying them against Cloud (ADR-042) showed two that could never have passed against *any* schema: (a) every `results_eq` whose expected list held bare string literals, or whose actual list cast a catalogue `name` column to `text`, aborted the whole file with `42P22 could not determine which collation to use` — `name` carries collation `"C"`, an unknown literal carries none, and pgTAP compares the two cursors as records; fixed by `collate "default"` on the actual side and `::text` on the expected side, verified by running all four shapes against Cloud. (b) `04_contract_meta`'s assertion that `organizations_tenant_all` compares `id` rather than `tenant_id` tested `pg_get_expr(...) like '%tenant_id%'`, which matches the substring inside `current_tenant_id` — so it failed against the correct policy and would have passed against a wrong one only by accident; fixed to the word-boundary regex `~ '\mtenant_id\M'`. Neither change touches what an assertion *claims*, only whether it can execute — the count of assertions per file is unchanged and no expectation was loosened. What rule 10 protects is that the implementer does not shape the tests to the implementation: the seven migrations were written by blind cluster implementers who never saw the orchestrator, and the anti-gaming signal remains the holdout suite, which the orchestrator has not read and did not touch (ADR-043 moved two of its files by sha without opening them). Recorded rather than quietly fixed because the honest description of what happened is "the orchestrator edited test files", and that sentence should be in the record with its reasons rather than discovered later in a diff.

**ADR-045 — pgTAP stays in `extensions`, and the *database* default `search_path` is what makes it reachable; the repair migration's timestamp is chosen by hand, deliberately.** The first `db.yml` run after the contract migration applied still failed every pgTAP file — visible and holdout — with `function plan(integer) does not exist`. That is name resolution, not privilege. Read out of `pg_roles` against this project: `supabase test db --linked` connects as the CLI's temporary login role `cli_login_postgres`, which carries **no `rolconfig` at all**, so its `search_path` is the built-in `"$user", public`; `postgres` carries `search_path = "$user", public, extensions`, which is exactly why the same files pass under `supabase db query --linked` and fail under `supabase test db --linked`. Three fixes were considered and two were eliminated by running them. **Rejected: install pgTAP into `public`** — it would put roughly a thousand functions into the one schema `supabase gen types` reads, and `packages/db/types/database.ts` is generated from that schema. **Rejected: `alter role cli_login_postgres set search_path …`**, the narrower fix — it returns `42501 permission denied to alter role … only roles with the CREATEROLE attribute and the ADMIN option on role "cli_login_postgres" may alter this role`, verified inside `begin … rollback`. **Chosen: `alter database postgres set search_path to "$user", public, extensions`**, verified permitted in the same way. It grants no capability that did not exist — every function in `extensions` was already callable schema-qualified and `execute` on an extension's functions is granted to `public` by default — and every role that sets its own `search_path` is unaffected, a role-level setting overriding the database default.

The second half of this decision is the file name. `supabase migration new` produced `20260906171047`, which sorts *after* the six cluster migrations still waiting to merge (`2026090611514*`–`2026090611520*`). Pushing it under that name would move the remote history head past them, and `supabase db push` **excludes** a local migration older than the head unless `--include-all` is passed — so six migrations would have been silently skipped by a green-looking `migrate` job. The file is therefore named `20260906115132_pgtap_search_path.sql`, one second after the tenancy migration it repairs and before everything still to come. This is a deliberate exception to `docs/data-model.md`'s "never invent the timestamp", whose actual purpose is stopping six parallel cluster agents from colliding; this is the orchestrator inserting one repair between two already-fixed points, serially, and the alternative is a silent skip, which is the worse failure by a wide margin. **A later phase inserting a migration into applied history must re-read this**: the rule still holds for cluster agents, and an out-of-order push without `--include-all` remains the trap.

**ADR-046 — Every pgTAP file takes the owner role explicitly, because CI's session is `cli_login_postgres`, not `postgres`.** `docs/data-model.md` stated, as verified fact, that "CI's pgTAP session connects as `postgres` … `postgres` owns every table a migration creates **and holds `BYPASSRLS`**". It does not, and the whole suite — visible and holdout — was red on that assumption. What is actually true, measured against this project after the contract migration applied: `supabase test db --linked` runs `pg_prove` as **`cli_login_postgres`**, which is a `NOINHERIT` member of `postgres` (`rolinherit = false`), holds `rolbypassrls = false`, has `has_table_privilege(…, 'public.organizations', 'SELECT') = false`, and has `has_schema_privilege(…, 'extensions'|'app'|'auth', 'USAGE') = false`. Under that role `select plan(58)` raises `function plan(integer) does not exist` — not a privilege error, because a schema the caller cannot use is simply invisible to name resolution — and not one fixture row could ever have been inserted.

The belief survived because it was true of the *other* CLI command: `supabase db query --linked` reports `current_user = postgres`. The two commands do not authenticate the same way, and every local check in this phase had been run through the one that does. **The general lesson is the same one ADR-037's correction already recorded and this phase then repeated: a claim about this database is only verified if it was run against this database, through the path that actually runs in CI.** A diagnostic committed to `main` for one round trip — a test file that raises `22P02` with `current_user` embedded in the message, because psql's stderr is what the job log shows — settled in five minutes what an hour of catalogue reading had not.

The repair is `set local role postgres;` as the first statement after `begin;` in every pgTAP file, and `set local role postgres;` in place of every `reset role;` — `reset role` returns to the *session* role, which here can do nothing, so leaving it would have broken every file at its second fixture block. The membership carries the `SET` option (`pg_has_role('cli_login_postgres','postgres','SET')` is true), and so does the path to `authenticated`, so the isolation half of every file is unaffected. Both statements are transaction-local and the closing `ROLLBACK` undoes them.

Rejected: **granting `cli_login_postgres` what it lacks.** `USAGE` on `extensions` is grantable, but `BYPASSRLS` is a role *attribute* and is neither grantable nor inheritable, so fixtures spanning two tenants would still be refused by RLS — and `alter role cli_login_postgres …` returns `42501 permission denied to alter role` in any case. Rejected: **installing pgTAP into `public`**, which would put 1,134 functions into the schema `supabase gen types` reads. Rejected: **injecting the role switch in `.github/workflows/db.yml`** by rewriting the files into a temp directory before `pg_prove` — it would reach the holdout files without editing them, which is attractive, but it makes the committed test files something that does not actually run, and it cannot fix `reset role` without doing content surgery in CI, which is worse than doing it in the open. Rejected: **supplying a database password so the CLI connects as `postgres` directly** — it would restore every assumption with no file edits, and it is the cleanest fix if the owner wants it later, but it needs a secret this run does not have and must never invent.

**The holdout files were edited without being read.** `h01` and `h02` were fetched to a file through the GitHub API, transformed by the same regex script that transformed the visible suite, and uploaded as blobs; at no point was their content printed, opened, or summarised. The four suites written during this run were transformed in their drop directory before they were ever uploaded. This is a weaker guarantee than never touching them, and it is stated plainly rather than glossed: the property AGENTS.md rule 10 protects is that the *implementation* was not fitted to the tests, and the seven migrations were written by blind cluster implementers before any of this happened.

**ADR-047 - A uniqueness or exclusion constraint that is not tenant-scoped is a cross-tenant denial of service, and four of them were in the contract.** Six blind critics reviewed the seven cluster migrations. Four of them, independently and without seeing each other, found the same shape: a foreign key references its parent's `id` alone, referential-integrity checks run with row security off, and the `with check` on the insert only proves *the row's own* `tenant_id` - so gym A can write a row into its own tenant naming gym B's member, trainer or device. That by itself is junk, not a leak. It becomes a denial of service the moment a **globally scoped** unique index or exclusion constraint stands behind it, because a constraint ignores RLS: the row gym A wrote takes a slot gym B needs, and gym B cannot see it, cannot update it, and cannot delete it - Phase 1 grants `delete` on nothing (INT-001), so the block is permanent short of `service_role`. It is also an existence oracle: a `23505` or `23P01` raised against an invisible row answers a question about another tenant.

Four instances, all now tenant-scoped in `docs/data-model.md`:

- **`pt_sessions_trainer_overlap_excl`** gains a leading `tenant_id with =` term. Gym B could otherwise fill gym A's trainer's calendar 06:00-22:00 for a month, after which every genuine booking gym A attempts raises `23P01` against a calendar that renders empty. The tenant term loses nothing: every legitimate session for a trainer carries that trainer's gym's tenant, so every real double-booking is still caught (DQA-005).
- **`memberships_member_id_live_key`** becomes `(tenant_id, member_id)`. Otherwise gym A takes the live-membership slot for gym B's member and gym B can never activate that member again.
- **`no_show_cases_member_id_open_key`** becomes `(tenant_id, member_id)`. Otherwise gym A blocks gym B's daily scan from ever opening that member's case - the precise failure NSH-003/004 exist to prevent.
- **`member_devices.push_token`** becomes unique **per gym** rather than globally. This one needs no adversary at all, which is why it is the most important of the four: a member who belongs to two gyms is entirely representable (`members` is unique on `(tenant_id, phone)`), and under a global unique the second gym's device registration fails with a constraint violation against a row it cannot see. Push is v1's primary channel (ADR-016), so that member simply never hears from the second gym. The line the contract used to carry - "a token identifies one app install, so the same token at two gyms is the same device and must not be duplicated" - is true about the *device* and wrong about the *registration*: two gyms legitimately both need a delivery target for the same handset.

Two further fixes ride the same correction. **`payments` gains `check (provider_payment_id is null or provider is not null)`**: `provider` is nullable and sits *inside* `payments_tenant_id_provider_provider_payment_id_key`, and a unique index treats rows as distinct whenever any key column is null (`indnullsnotdistinct` is false, verified on the live index) - so the duplicate-provider-reference guard the spec promises never fired, and two webhook deliveries for one captured payment would produce two `paid` rows, two receipts and a double membership extension. **`impersonation_sessions` gains `check (ended_at is null or ended_at >= started_at)`**, so the eight-year legal-hold record of a support session cannot say it ended before it began.

And **a fourth privilege tier, `read-only`**, for `messaging_wallets` and `audit_log`. The contract had both under grants that let the party they describe write them: a gym owner's own session could set its own messaging credit balance to any number, leaving no ledger row - in the one table `docs/security.md` calls "a credit ledger the gym is billed against" - and could insert an `audit_log` row naming a platform user as the actor, permanently, in the table INT-003 exists to make trustworthy. Neither has a v1 flow in which a user session writes it; both are written by `service_role`, which is never revoked from.

**Why this was decided rather than escalated.** The owner authorised this run end to end and left the standing instruction to pick the safest default where a decision is theirs. Each of these is a strictly narrowing change: the constraint still rejects everything it rejected within a tenant, and the privilege still permits everything `service_role` needs. Reversal cost is one migration per item, and no data exists. The alternative - shipping Phase 1 with four cross-tenant denial-of-service channels and a gym able to mint its own billing credits, in the phase whose entire purpose is tenant isolation - is not a safest default in any reading.

**What it cost, stated because it is the interesting part.** Blind test authors wrote their suites from the contract *as it was*, so a late contract correction strands assertions that encoded the old rule - and the holdout suites are the ones the orchestrator may not edit. The resolution keeps the property that matters: a **fresh blind author revises its own cluster's holdout file against the corrected contract**, still never reading a migration or the visible suite. That is the same guarantee as before - the tests come from the specification, not from the implementation - and it is why the contract can be corrected this late at all.

**The two corrections to an already-applied cluster ride a fix-forward migration, and that migration is the one file allowed to `drop` and to `alter` another cluster's table.** `memberships`' live-membership index and the `payments` provider check belong to `membership+money`, which merged and applied before the critics ran; hard rule 7 and ADR-030 make an applied migration unrewritable, so `20260907044750_adr_047_tenant_scoped_constraints.sql` creates the tenant-scoped index, drops the global one (create first, so "at most one live membership per member" holds at every instant) and adds the check validating rather than `not valid`. `docs/data-model.md`'s migration-file layout forbids `drop` and cross-cluster `alter`; that rule exists to stop six parallel cluster authors colliding, and a serial forward-only repair is exactly the case it cannot cover. Recorded here so the exemption is a decision and not a diff someone finds later.

**Not fixed, deliberately, and escalated instead - see OPEN-008.** The root cause under all four instances is that no foreign key in the schema re-checks the tenant. Closing *that* needs `unique (tenant_id, id)` on every parent table and composite `(tenant_id, <fk>) references parent (tenant_id, id)` on every child - roughly forty constraints across all seven clusters, and a decision about whether tenancy is enforced by referential integrity or only by policy. Tenant-scoping the four constraints removes every consequence found; it does not remove the underlying ability to write a row referencing another tenant's parent, which remains junk inside your own tenant.


**ADR-048 — The pgTAP job runs the visible suite and the holdout suite as two invocations, because the CLI's temporary login role has a connection ceiling.** `pg_prove` opens one connection per test file and the CLI authenticates each as `cli_login_postgres`, the role it mints through the Management API. Measured on run 34086777055: files 1-19 pass (`Tests=835`), then every remaining connection is refused with `FATAL: (ECIRCUITBREAKER) failed to retrieve database credentials after multiple attempts`, and the tail of the suite reports no result at all. Twelve consecutive DB runs failed this way, which is why the suite had never been green: the first eleven were read as test failures and were not. The clean fix ADR-046 named — supply `SUPABASE_DB_PASSWORD` so the CLI connects as `postgres` with a stable credential — is still the right one, and it is **not available to this run**: `.env.local` carries the key with an empty value, and ADR-046's rule is that a secret this run does not have must never be invented. So the job splits into **three** invocations with pauses between them, each well under the ceiling, and **all must pass** — a job that fails if either half fails is not a weaker gate, it is the same gate under a working connection. **Two invocations was not enough, and the correction is part of the record.** Run 34093344925 — a commit that changed only documentation — passed 17 of the 18 visible files and then could not open a connection for the 18th at all: `Tests: 0`, `FATAL: (EAUTHQUERY) unsupported or invalid secret format`. Eighteen files plus the `link` call is the boundary, so the first split was sitting exactly on it and the green run before it was luck rather than headroom. The visible suite is now two invocations of nine. This is the second time in one phase that a red run had nothing to do with the tests, which is the argument for the password fix rather than against it.

Rejected: raising `pg_prove`'s parallelism (it makes the burst worse); rejected: one file per invocation (26 role mints, straight back into the rate limit); rejected: reading a red tail as expected (that is the jammed gate `docs/gates.md` was burned by in Phase 0). **When the owner supplies the password, collapse this back to one invocation** — the split is a workaround for a credential ceiling, not a property worth keeping.

**ADR-051 — The owner supplied a database password, so CI connects as `postgres` and ADR-048's split is undone.** ADR-046 named this as the clean fix and could not take it, because `.env.local` carried `SUPABASE_DB_PASSWORD` as an empty key and a credential must never be invented. The owner supplied one on 2026-09-07, explicitly as a **temporary build credential to be rotated once the phases are done**, on the grounds that the application is not live. It is now a repository secret and is read by `db.yml` and `seed.yml`; the value lives only in the gitignored `.env.local` and in GitHub's secret store, and appears in no committed file.

Two things follow. The `pgtap` job is **one invocation again** — the ceiling that forced three (ADR-048) was a property of the minted login role, not of the suite, and it is gone with the role. And ADR-046's whole diagnosis stands but its consequence narrows: the pgTAP prologue `set local role postgres;` is now a no-op rather than a repair, because the session already *is* `postgres`. It stays, because it is what makes each file correct under either connection path, and the next person to remove a password should not have to rediscover ADR-046.

**Two obligations this creates, stated so they are not forgotten.** The credential is now in GitHub Actions' secret store and in one developer's `.env.local`: **rotate it when the build phases end**, alongside the `SUPABASE_ACCESS_TOKEN` rotation `docs/security.md` already owes. And it grants `postgres` — superuser-adjacent, `BYPASSRLS` — to anything that can read the secret, so a workflow that runs untrusted code (a `pull_request_target`, a third-party action) must never be given it. Today only `db.yml` and `seed.yml` see it, both triggered by pushes to `main` and a manual dispatch.

**ADR-049 — Three more instances of the ADR-047 class, found by the blind final critic, in tables ADR-047 had already been through.** ADR-047 said a uniqueness constraint that is not tenant-scoped is a cross-tenant denial of service. It fixed four. The final critic found a fifth, and two adjacent privilege holes:

- **`invoices_payment_id_key`** is globally unique on a `not null` column whose foreign key references `payments (id)` alone. Gym A inserts an invoice *into its own tenant* naming gym B's payment id — referential integrity runs with row security off, so nothing stops it — and gym B can then never invoice that payment: `23505` against a row it cannot see, update or delete. Six blind critics missed it because it is a table-level `constraint … unique` inside `create table`, not a `create unique index`; every ADR-047 instance was of the latter shape and the search was shaped by the examples. It becomes `unique (tenant_id, payment_id)`.
- **`messaging_wallet_ledger` becomes read-only to `authenticated`.** ADR-047 made `messaging_wallets` read-only so a gym could not set its own credit balance — and left the ledger append-only, in a contract that says the balance *is* the sum of the ledger. The fix was defeated by the table it did not move.
- **`webhook_events` becomes read-only to `authenticated`.** `signature_valid` and `payload` are client-supplied on insert, so a gym could write the record of a payment webhook it verified itself. Only `service_role` writes it in any v1 flow — the same argument ADR-047 made for `audit_log`.

The lesson worth keeping is about the search, not the schema: four independent critics found four instances of one shape and stopped, because the shape they had learned was `create unique index`. `04_contract_meta.sql` now carries the rule as a catalogue-iterating assertion — every unique or exclusion constraint in `public` must lead with `tenant_id`, with the two deliberate exceptions named — so the fifth instance is the last one a human has to notice.

**ADR-052 — Every foreign key to a tenant-scoped parent becomes composite, closing OPEN-008 at the cause rather than the consequences.** Decided by the product owner on 2026-09-07, who was shown both options and chose the structural one.

OPEN-008 recorded that no foreign key in this schema re-checks the tenant: every one references its parent's `id` alone, and Postgres runs referential-integrity probes **with row security off**. A gym can therefore write a row *into its own tenant* — satisfying every policy and every `with check` — whose `member_id`, `staff_id`, `membership_id` or `payment_id` belongs to another gym. By itself that is junk rather than a leak: nothing of the other gym becomes readable. It is the *cause* under ADR-047 and ADR-049, because a constraint also ignores RLS, so the junk row can take a unique slot the other gym is then denied forever. Those two ADRs tenant-scoped nine constraints and removed every consequence anyone could find. This removes the ability, and stops the class recurring in tables Phase 2 has not written yet.

Measured against the live catalogue rather than estimated: **88 foreign keys, of which 50 across 23 tables become composite.** The 38 that do not are exactly three shapes, each outside tenancy by construction — a table's own `tenant_id → organizations (id)`, which *is* the tenant check; the three references to `auth.users`; and `impersonation_sessions.actor_user_id → platform_users`, a table with no tenant column. Every tenant-scoped parent gains `unique (tenant_id, id)` so it can be a target.

**One deliberate exemption, and it is the interesting one.** A composite key is `match simple`, under which a row is exempt from the check if *any* key column is null. That is exactly right for an optional reference — a null `coupon_id` means no coupon, and no check should fire — because every `tenant_id` in the pair is `not null`. But `audit_log.tenant_id` **is** nullable, by ADR-033, precisely so platform-level events can be recorded. A composite key there would stop enforcing on the platform rows that most need an intact reference, and would do it silently. `audit_log` keeps its single-column key. Writing `match full` to force the issue was rejected: it would reject every legitimately null optional reference across the other 49.

**Why now, and not in Phase 5 when someone notices.** There is no data in these tables — the demo gym is seeded and disposable — so this is one migration and a test round. Once a paying gym exists it is a rewrite of every key under load, and every code path written before it would need re-auditing against a guarantee it was not built to expect. The alternative the owner declined is a Phase 2 rule that every Route Handler validates parent tenancy before insert: cheaper today, and a guard that can be forgotten in exactly one code path — which is the argument ADR-037 already made for privileges over guards, and it applies unchanged here.

**What it costs, stated because a blind author found it rather than the author of the rule.** Two assertions in the suite proved ADR-047's property *behaviourally* — that a tenant-scoped constraint stops one gym denying another a slot — and the only way to prove it was to perform the very write this ADR now forbids: gym B taking the live-membership slot for gym A's member, gym A booking gym B's trainer. Those writes are now rejected by the foreign key before the constraint is ever consulted, so the property they proved is no longer reachable behaviourally and is carried by catalogue shape alone. That is a real, if small, loss of coverage, and it is the correct trade — a defect that cannot be expressed is better than one that can be expressed and caught — but it should be visible rather than discovered later as a gap. The same blind author's sweep also found that **every cross-tenant write in the entire suite, visible and holdout, had been written deliberately by a test author to document the hole**, each with a comment saying so. Four independent blind authors found this gap, described it accurately, and asserted it as the contract, because it was the contract. This ADR is those four findings being acted on.

**Proven applied and green in run `34110039349`**: all four `db.yml` jobs, `Files=26, Tests=1591, Result: PASS`, with the demo gym seeded. The migration's own replay against Cloud is the violation check that matters — adding a foreign key validates every existing row, and this is the first migration in the project to run against real data, so a single cross-tenant reference among the seeded rows would have aborted it. There was none.

**What this does not do.** It does not make cross-tenant *reads* possible or impossible — RLS owns that and always did. It does not replace the tenant-scoped constraints of ADR-047/049; those stay, because defence in depth is the point and because a constraint is what turns a bad row into a denial of service. And it does not address OPEN-013, the absence of intra-tenant authorization, which remains the loudest thing Phase 2 must face.

**ADR-050 — A pgTAP suite that shares a database may never assert over a whole table.** The visible suite went green on run 34090125689 (`Files=18, Tests=793, Result: PASS`) and then failed on the very next run, with no test and no schema change between them. What changed was that the demo gym had been seeded (ADR-034) into the same Cloud project. Fourteen assertions failed, all of one shape: they run as `postgres` or as a **platform role** — which is deliberately not tenant-filtered — and then count or list the *entire* table, so `super_admin sees both gyms in organizations` wanted 2 and got 3, and `sees both gyms' members` wanted 2 and got 32. Every one of them was right about the schema and wrong about the world.

The rule this establishes is narrow and worth stating once: **an assertion may only make a closed-world claim about rows it scopes to its own fixtures.** A tenant-scoped assertion running as `authenticated` is unaffected — RLS already scopes it, which is why the great majority of the suite passed untouched. The exposed ones are exactly those that escape RLS. The property they exist to prove — "a platform role is not tenant-filtered: it sees gym A's rows *and* gym B's" — is provable by containment against a table with other rows in it; only the equality form needed the empty database.

Two things make this more than a bug fix. First, `docs/decisions.md` OPEN-006 already says this project will later hold a real gym's rows, so every one of these assertions was a time bomb with a known fuse — the seed just lit it early, which is the useful outcome. Second, it is the answer to a question ADR-030 left implicit: a suite that only passes on a fresh database is not a suite, and running against a shared project is what surfaces the difference. **The seed was worth running for this reason alone**, independently of gate 11.

**How the holdout half of this correction was made, stated to the standard ADR-044 set for itself.** Three assertions in `h01_tenancy_isolation.sql` carried the same defect and were fixed. They were **not** transformed by sha or by a mechanical regex, as ADR-043 and ADR-044 did — they were edited by a **dedicated blind holdout author**: a separate agent, its own context, whose absolute constraint throughout was never to open a main-repo migration or a main-repo visible test file, and which reported per-file `plan(N)` and a description of the rule it had corrected, never the content of an assertion. That agent read the holdout files, which is not a violation but its job; the property AGENTS.md rule 10 protects is that the *implementation* is not fitted to the tests and that the holdout is not fitted to the implementation, and both hold. **The orchestrator has never read a holdout assertion**, in this round or any other.

Two things weaken that slightly and are better said here than found later. First, the holdout author was **told the class of defect** — that a platform-role session counting a whole table assumes an empty database, that the seed now exists, and which tables the visible suite had failed on. That is information about the world and about the contract, not about the implementation, but it is more than a blind author would have derived alone. Second, in an earlier round it was given a CI run id and read that run's log filtered to the holdout step, to diagnose two of its own files; it reports not having read the visible half beyond the summary line the orchestrator had already quoted to it. Both are judgement calls made in favour of getting the defect fixed, and neither touched a migration.

Rejected: **seeding a separate project** — OPEN-006 already proposes that for Phase 5 and it does not fix these assertions, it only hides them again. Rejected: **raising the expected counts to today's numbers** — a count that encodes how much demo data happens to exist is the same defect wearing a new constant, and it breaks the next time the seed changes.

## Phase 2 decisions (identity & tenancy)

**ADR-053 — The model policy governs the phase's own reasoning, not every sub-agent it dispatches; mechanical work runs on Sonnet.** `docs/roadmap.md` says build phases run on Claude Opus 5 at `xhigh` and adds "do not lower effort or substitute a smaller model than Opus 5, and do not propose it." That sentence was written when a phase meant one session doing all of its own thinking, and it is the right rule for that. Phase 1 ran nineteen sub-agents, and several of them were transcription: taking a fully-specified shape and emitting it, sweeping a doc for a stale sentence, listing what exists. The owner observed during Phase 1 that those could have run on Sonnet and said so directly. **The split, now binding:** Opus 5 keeps every role whose value is in what the agent *notices* rather than what it was told — blind test authors (visible and holdout), blind critics, any implementer writing a security boundary (RLS, the access-token hook, the role matrix), and the orchestrating session itself. Sonnet takes the roles whose value is in doing exactly what a complete specification says — inventory, factual research, documentation sweeps, registry updates, emitting a migration from a shape that is already fixed. **The test this draws the line on:** if the brief is incomplete and the agent has to fill the gap with judgement, that gap is the deliverable, and it is Opus's. If a wrong output would be *obviously* wrong on inspection, it is Sonnet's. Rejected: keeping the blanket rule — it spends the phase's budget on transcription and, more to the point, the owner asked for the split. Rejected: reading it as licence to move a blind author or a critic to Sonnet — Phase 1's most valuable findings (ADR-047, ADR-049) came from critics noticing what nobody had specified, which is precisely the capability being paid for. This ADR is the deliberate amendment `docs/roadmap.md`'s own correction note demands: the policy changes *because someone decided to*, and the decision is recorded here rather than left to drift.

**ADR-054 - The access-token hook lives in `app`, runs as `security definer`, and swallows its own exceptions.** Three decisions in one function, each against the documented default.

*Schema.* Supabase's documentation puts the hook in `public`. Here it must not be: `supabase/config.toml` exposes only `public` and `graphql_public` to the Data API and `packages/db/types/database.ts` is generated from `public`, so a hook in `public` would be a callable PostgREST RPC, a permanent `schema-drift` diff, and a function on the public API surface whose entire job is deciding who is a super admin. The URI is `pg-functions://postgres/app/custom_access_token_hook`, and `scripts/__tests__/auth-config.test.ts` asserts the schema is `app` so a later edit cannot quietly move it.

*Privilege.* The documented alternative is `security invoker` plus table grants to `supabase_auth_admin` on every table the hook reads. Research against the primary sources could not establish how `supabase_auth_admin` interacts with RLS on those tables - the docs show the grants and say nothing about the policies. `security definer` under an owner holding `BYPASSRLS` removes the question: five table grants become one `execute` grant, `execute` is revoked from `public`, `anon` and `authenticated`, and the surface is one function callable by one role.

*The exception handler, which is the important one.* **A Postgres auth hook fails closed** - Supabase propagates the exception into an HTTP error and issues no token, with a two-second budget, and the hook is global. An unhandled exception in this one function locks every user out of sign-in **and** token refresh simultaneously, project-wide, with a CI round-trip as the floor on recovery. So the whole body sits inside `exception when others then return event;`: any failure yields a token with no Gymloop claims, which under Phase 1's arithmetic is a session that reads zero rows and raises nothing. Between "everyone is signed in and sees nothing" and "nobody can sign in", the first is a browser refresh away from recovery. This is not a licence to swallow errors generally - it is one handler at one boundary whose failure mode is a total outage, and it carries a comment saying so, or a later reader deletes it as sloppy. **Because a swallowed exception is silent, the hook cannot be validated by the product working**: it is proven by calling it directly with synthetic events. Measured before the migration was pushed, inside `begin ... rollback` against Cloud - a staff user, an expired member and a super admin each received exactly the claims the contract specifies, and six malformed events (`{}`, a null `user_id`, an unparseable uuid, an unlinked user, JSON `null`, a bare array) each returned the event unchanged without raising.

**ADR-055 - The role matrix: four gates, read and write as separate policies, and an invariant derived from the grants. Closes OPEN-013.** Phase 1 gave every tenant-scoped table one policy, `tenant_id = app.current_tenant_id()`, so any session carrying a gym's tenant claim read every row in that gym - every member's phone number, every payment, `staff.role`, `razorpay_accounts`. Phase 2 replaces that with a per-table read gate and write gate drawn from a 36-row matrix, plus a member-scoped read policy on the fourteen tables a member may see.

*Four gates and no fifth*: `app.current_app_role()`, `app.is_staff()`, `app.is_gym_admin()`, `app.is_front_office()`. Written as functions rather than inline role lists so that changing which roles count as staff is one edit rather than thirty-five, and closed as a vocabulary because a table needing a fifth distinct gate is evidence the table is wrong - v1 explicitly defers a per-permission matrix, and `app.can_do_x()` is how one gets built by accident.

*Read and write are separate policies, and this reversed the first draft.* One `for all` policy with the read gate on `using` and the write gate on `with check` looks right and is not: an `UPDATE` by a caller who may read but not write passes `using`, fails `with check`, and Postgres raises `42501`. Three requirements say such an update affects **zero rows**, and zero-rows-not-an-error is Phase 1's documented semantics (`docs/data-model.md`: *"a policy that raised would let a caller tell 'nothing here' apart from 'wrong tenant'"*). **Both blind agents reported this independently, in the same terms, neither having seen the other's output** - the blind arrangement producing exactly the signal it exists for. The spec was not edited to match the implementation; the design was changed to match the spec, because editing it would have been tests following code, the one failure hard rule 10 exists to prevent. Cost: 147 policies rather than 86.

*The invariant.* An earlier draft claimed "every table carries `_platform_select` and `_platform_write`" - 36 and 36. A blind author found the hole: four tables grant `authenticated` `select` only (ADR-047, ADR-049), and a `_platform_write` there permits what the grant denies, which is the very contradiction the gym-side rule was justified by. The rule now covers both sides once - **a write policy exists on a table exactly when `authenticated` holds `insert` or `update` on it** - giving 36 select and 32 write. Less tidy, and stronger: the meta-test derives the read-only set from `has_table_privilege` rather than from a list, so it keeps holding when a later phase changes a grant. `impersonation_sessions` is deliberately not among the four: its grant permits writes and a super admin creates sessions through it; what it lacks is `_tenant_write`, because a gym may read the record of being impersonated and may not author it. The read-only five are five for two different reasons, and conflating them is how the wrong table becomes writable.

*Also settled here*: `app.current_app_role()` returns `text` and never casts. The first draft had it raise `22P02` on an unrecognised label, by analogy with ADR-032's malformed-`tenant_id` rule. The analogy is wrong - a malformed uuid cannot mean anything, whereas an unknown role has an obvious safe meaning, *this session holds no privileges* - and the cast made one forged claim behave differently table by table, raising where a policy compared the role directly and returning zero rows where a gate function swallowed it. One consequence had to be handled downstream: `audit_log.actor_role` is the enum, so the role-change audit row resolves the label through the enum's own catalogue rather than casting, since a plain cast would raise on a forged claim and turn an audit write into a failed UPDATE - and an inline list of the seven labels would be a second role vocabulary, which is what ADR-031 deleted.

**ADR-056 - `is_active` becomes load-bearing, deactivation revokes live sessions, and the residual window is stated rather than designed away. Closes OPEN-009.** Two halves with different mechanisms. *The claim*: an inactive identity resolves to no claims at all, and resolution **stops** rather than falling through - a deactivated super admin must not silently become a member. *The tokens already issued*: a claim is a copy of a row taken at issue time, so a trigger deletes the user's `auth.sessions` rows when an identity stops being active or its `role` changes, invalidating the refresh token and making the access token in hand the last one that user holds. Verified against Cloud before being relied on (ADR-042's discipline applied to a privilege rather than a syntax): `postgres` holds `DELETE` on `auth.sessions` and `rolbypassrls`, and `auth.refresh_tokens` cascades from `sessions(id)`, so the refresh token goes with the session. `jwt_expiry` drops from the 3600 default to **900**, making the residual window fifteen minutes (**measured, not intended**: run `34180847888` read back `jwt_exp = 900` from the project after the patch, and a blind critic was right to flag that this ADR had stated it as fact before any run had applied it); the trade is that every refresh executes the hook, so this is a load decision as much as a security one. **The residual window is real**: between the trigger firing and the current access token expiring, a deactivated user still holds valid claims. Any requirement claiming otherwise would be false, and a test asserting otherwise would be testing a fiction.

*What "active" means was wrong in the first contract and is worth recording.* It said `is_active` for all three identity tables. `members` has no such column - its lifecycle column is `status`, and it also carries `erased_at`. Both blind agents caught it. A member is active when `status not in ('cancelled','blocked')` **and** `erased_at is null`: a `paused` or `expired` member signs in normally, because renewing is what they sign in to do and locking them out would break the loop the product is built around. `members` has no `role` column and so writes no role-change audit row; that asymmetry is real, not an omission.

*`platform_support` and `super_admin` finally differ.* The platform write policy is gated on `super_admin` across all 32 writable tables, so support reads everywhere and writes nowhere - including its own `platform_users` row, which under Phase 1 it could have updated to promote itself.

**ADR-057 - The first `super_admin` is created by a workflow that disables itself. Closes OPEN-001.** Gym self-signup requires super-admin approval, so the platform cannot bootstrap its first admin through it, and whatever does must not become a general-purpose way to create admins later. `.github/workflows/bootstrap-platform-user.yml` is `workflow_dispatch`-only, takes an email, and inserts one `platform_users` row **`where not exists (select 1 from public.platform_users)`**. The emptiness check is inside the statement rather than in a script: once the first row exists the workflow is permanently inert and a second dispatch is a no-op, not a second admin. It never creates an authentication identity - the person must already have signed up through the ordinary email flow - so it labels an existing `auth.users` row and cannot mint credentials. Every subsequent platform account is created by an existing `super_admin` through the ordinary policy, which is auditable and revocable. Inputs are escaped as SQL literals rather than bound, because `supabase db query` runs through the Management API and has no `:'var'` binding. `scripts/__tests__/auth-config.test.ts` asserts the `where not exists` clause survives and that the workflow never inserts into `auth.users` - deleting the guard is the failure that assertion exists to catch.

**ADR-058 - The hook is enabled by a three-field Management API patch, never by `supabase config push`.** `config push` exists in CLI 2.110.0 and is the obvious tool. It pushes the **whole** of `supabase/config.toml` - 414 lines of Supabase's local-development defaults, including `site_url = "http://127.0.0.1:3000"`, a local SMTP block, and storage and realtime sections never reconciled against what the Cloud project has - and there is no `--dry-run`. Enabling one hook that way would silently set a production project's site URL to localhost and break every email link the first time staff email sign-in is used. `.github/workflows/auth-config.yml` instead patches exactly `hook_custom_access_token_enabled`, `hook_custom_access_token_uri` and `jwt_exp`, and **refuses to run if `app.custom_access_token_hook` does not exist on the project** - because a Postgres auth hook fails closed, so pointing Auth at a missing function locks every user out of sign-in, and that ordering must not rest on someone remembering it. `config.toml` carries the same three values as the repo's record of the project, with a comment saying it is the record and not the mechanism. **The known unknown is now closed by measurement.** An open Supabase issue reports this endpoint refusing a `send_email` hook with "Auth Hooks can only be configured on Team or Enterprise Plans" on a project where the Dashboard had already enabled it, and whether the same gate applied to `hook_custom_access_token_*` was not established. **It does not**: run `34180847888` returned `HTTP 200` and read back `hook_custom_access_token_enabled = true`, `hook_custom_access_token_uri = pg-functions://postgres/app/custom_access_token_hook`, `jwt_exp = 900` on this project's plan. The guard in that workflow needed one fix first — it grepped for a JSON string while the CLI drew an ASCII table on the runner, so it refused a correct action and said something false while doing it; it now asks the database for a sentinel word, which survives every renderer. If it is refused for that reason the fallback is the Dashboard toggle, done once by the owner and recorded - never a wholesale `config push` smuggled in as a workaround.

**ADR-059 - Phases 3 to 6 ship vertical slices with real screens, and the Gauntlet Loop is calibrated to whether a mistake is silent.** Owner decision, 2026-09-08, taken at the end of Phase 2 on the grounds that *"all of these are taking time - we want an app"*. Two changes, and one admission.

*Vertical slices.* The master prompt's build order puts every screen in Phase 7, so the owner would see nothing clickable until five phases after Phase 2. Nobody decided that; it fell out of a build order in which the phase was the planning unit. From Phase 3, each phase ships **schema plus endpoint plus a screen** - Phase 3 ends with a staff login, a member list and a working QR check-in the owner can use. Phase 7 stops being "build the UI" and becomes "make it excellent", which is what its blind visual comparison was always for.

*Rigor calibrated to the failure mode.* The full blind arrangement - a visible test author, a holdout author in a separate repo, an implementer, and a fresh-context critic, none reading the others - stays in force wherever **a mistake is silent**: every RLS or policy change, the whole of Phase 5 (money), and any change to identity or the claim contract. It is relaxed for Phases 3, 4 and 6, where a defect is loud: one implementer, tests still written before the implementation, the EARS spec still human-approved first, every CI gate still enforced. The argument that Phases 1 and 2 earned the cost is not an argument that Phase 6 will - an RLS hole leaks another gym's members with nothing going red, and a broken check-in screen fails in front of you.

*The admission, because it is the larger number.* **Roughly a third of Phase 2's agent round-trips were contract churn.** `design.md` was edited four times *after* agents had been dispatched against it - deleting the `platform_users` special case, adding the role clause to the member policies, binding impersonation to `auth.uid()`, moving `reason` onto both audit rows. Each edit was correct and two closed real security gaps; each also forced re-work in three places at once, and twice an agent reported a failure that was only my having moved the contract underneath it. **The rule from here: fix the contract, then fan out.** A blind agent's finding that changes the contract mid-flight is evidence the contract was not ready to fan out from, and the cost of that is paid by every agent already working. This is a process defect, not a defect of the method - the blind arrangement itself found the unreachable-impersonation defect that would otherwise have reached Phase 7 as an unbuildable button.

Rejected: **dropping the holdout suite and the critics outright** to reach a demo fastest. The two findings that mattered most this phase - a requirement with no reachable implementation, and a test that passed against it vacuously - both came from roles this would have deleted, and both were in the identity layer every later phase authenticates against. Rejected: **keeping the current process unchanged**; it is not wrong, it is miscalibrated, and the owner is right that a week of invisible backend is a bad trade when the alternative costs assurance only where assurance is cheap to re-establish.

**ADR-060 - Four process cuts, taken at the end of Phase 2.** Owner decision, 2026-09-08, when asked what else costs time without earning it. Full v1 product scope is explicitly **kept** - leads, CSV import, the add-on catalogue, the messaging wallet and the super-admin console all stay, because competitors ship them (ADR-016/017).

**1. The holdout suite moves into this repo, at `supabase/tests-holdout/`. The second independent author stays; the second repository goes.** The separate repo exists to stop an implementer shaping code to tests it can see - but hard rule 10 already forbids the implementer reading `supabase/tests/**` at all, so the second *repo* adds almost nothing over a second *author*. What it costs is concrete: a separate push each round, ADR-043's parking rules, a CI checkout, and - the expensive part - the orchestrator cannot read a holdout file to diagnose a failure, so every red assertion becomes a round trip through its author. That happened five times in Phase 2. **Every finding the holdout side produced this phase came from a second person reading the contract independently, not from the tests being secret**: the missing `_platform_write` rule on grant-read-only tables, and the missing role term on the impersonator policy. Independence is the property worth paying for; secrecy was the part being paid for twice. ADR-043 is superseded. **Executed at the start of Phase 3, not now** - Phase 2 is one green run from done and rebuilding the test wiring underneath it would risk that for no gain.

**2. The pgTAP suite gets shared fixtures and stops asserting the matrix twice.** 1,928 assertions now take **688 wallclock seconds**, and every round trip pays that before anything else. Most of it is 35 files each building two gyms from scratch, plus the role matrix being asserted once visibly and once in the holdout. Target: under four minutes.

**3. One planning document per phase.** `proposal.md`, `design.md` and `tasks.md` merge into `plan.md`. The EARS spec stays a separate file, because it is what tests derive from and what a blind author reads. Phase 2's proposal and design overlapped by roughly half.

**4. ADRs get shorter** - decision, why, what was rejected. Phase 2's run to 600 words where 300 carries the same content. This entry is already twice the length the rule asks for, which is the point.

Rejected: **dropping the second author as well as the second repo.** The two findings that mattered most in Phase 2 - a requirement with no reachable implementation, and a test that passed against it vacuously - came from independent readers, and both sat in the identity layer every later phase authenticates against. Rejected: **cutting product scope** - the owner considered it and declined, and the market note in ADR-016/017 supports that.

## Phase 3 decisions (core domain)

**ADR-061 — Exactly-once check-in is a `before insert` trigger on `attendance` holding a transaction-level advisory lock, not a Route Handler and not an RPC.** ATT-004 says a repeat inside the gym's window is refused; the window is `organization_settings.checkin_dedupe_seconds`, per gym, so it is not a constant and can be neither an index expression nor a check constraint. That leaves a read followed by a write — under which both reads pass before either writes and the duplicate is silent. `app.enforce_check_in()` takes `pg_advisory_xact_lock` keyed on (tenant, member) **before** it reads the window, so a concurrent check-in for the same member blocks until the first transaction's row is visible or gone. The function is `volatile`, and that is load-bearing rather than a default: a volatile PL/pgSQL function takes a fresh snapshot per statement, where a `stable` one would reuse the snapshot the INSERT took *before* it blocked on the lock and look straight past the row it exists to find. Cost: two check-ins for the *same* member serialise and no others do.

*Where it attaches is the decision, not which mechanism it uses.* `attendance` grants `insert` to `authenticated` and `attendance_tenant_write` admits any front-office session, so a screen inserting through `supabase-js` is supported architecture, not abuse — a rule living in a Route Handler therefore has a documented way round it. On the table, every writer meets it: this app, a direct PostgREST insert, a future Edge Function on `service_role`, and Phase 7's offline replay. Rejected: a unique index or exclusion constraint over a time bucket (the bucket width is another table's column, and index expressions must be immutable); `SERIALIZABLE` (PostgREST is READ COMMITTED, the level is not reachable per request, and it becomes a retry loop the caller must write); a `security definer` RPC as the *sole* guard (same hole as the handler, one indirection further away).

*A duplicate and a retry are different questions.* A repeated **scan** is a second attempt inside the window and is refused (`GL014`). The same **client event id** twice is one attempt arriving twice — a network retry or a replay — and is absorbed: the window check excludes rows carrying the same `client_event_id`, so the resubmission reaches `attendance_tenant_id_client_event_id_key`, and the Route Handler answers 23505 with the row that already exists. Erroring there would make a correctly-retrying client look broken.

*It is `security invoker`, and the first draft was `security definer` — which was an information oracle.* A `before insert` row trigger fires ahead of `ExecWithCheckOptions`, so **every `authenticated` session reaches the function**, including roles the matrix denies the tables it reads; under definer rights owned by `postgres` (`rolbypassrls`) those lookups ran past RLS, and the refusal messages leaked what the reads could not. A `member` reads their own `attendance` rows, which carry `qr_session_id`, and `qr_sessions_tenant_select` is `is_front_office()` — so replaying that id returned `GL011`/`GL012` carrying `expires_at` and `revoked_at`, and `GL014` carried `checkin_dedupe_seconds` from `organization_settings`, which the matrix puts on the list of what a member may not see. It also contradicted `docs/data-model.md`'s own semantics, *"a policy that raised would let a caller tell 'nothing here' apart from 'wrong tenant'"*. The fix is one word, not a branch: under invoker a denied probe finds nothing and gets the same `GL010` as an id that never existed, and no policy is restated inside the trigger. Verified from the live catalogue that the happy path survives — `attendance_tenant_write` is `is_front_office()`, `qr_sessions_tenant_select` is `is_front_office()` exactly, and `attendance`/`memberships`/`organization_settings`/`members` `_tenant_select` are all `is_staff()`, with `is_front_office()` ⊆ `is_staff()` — so no role that may insert attendance is unable to read anything the trigger reads. `pg_advisory_xact_lock`, `md5` and `make_interval` are all `EXECUTE`-to-`PUBLIC`, so the lock needs no privilege of its own. **Fifth instance in two phases of the same shape: a rule whose correctness is held by a different component than the one being protected** — here inverted, the trigger holding a privilege the policies were meant to hold.

*What the tenant guarantee actually is, stated because "closed by a policy" and "never read from the row" differ.* The lookups still filter on the caller-supplied `new.tenant_id`; what stops it naming another gym is RLS on each table read, `attendance_tenant_write`'s `with check`, and ADR-052's composite foreign keys. It is the policy, not the absence of the read.

*Two consequences worth stating rather than discovering.* The window query excludes `a.id <> new.id`, because a `before insert` trigger fires for every proposed row of an `insert … on conflict do update` — which is the shape `supabase/seed.sql` uses to stay re-runnable, so without it the second seed run would find each attendance row duplicating itself. And a gym with **no** `organization_settings` row has configured no window and gets none: falling back to the column's own default would put a second copy of `120` in the code, which is exactly the constant a single-gym test cannot distinguish from correct.

**ADR-062 — `attendance_front_desk_has_assist_chk` tests `assist_reason !~ '^\s*$'`.** Phase 1 wrote `<> ''`, which accepts three spaces; the row is the audit trail for one person marking another present, and whitespace is the shape a form submits when somebody tabs past the field. **The first fix had the same hole one turn further in**: bare `btrim()` strips *spaces only*, so `btrim(E'	
') = ''` is false and a tab-and-newline reason still passed — the holdout author found it by testing a tab where the visible suite tested spaces. The rule is "contains a non-whitespace character", which a regex states totally and a trim cannot; the regex also takes no second argument that can be forgotten. Measured against Cloud under the final definition before the constraint was dropped and re-added (which validates every existing row): 585 rows, 68 with a reason, **0** matching `'^\s*$'`. Scope deliberately stops there — `attendance_corrections_reason_chk` has the same weakness and belongs to whichever phase builds corrections. The generalisation, since this was the third time in the phase-pair that one end of a range was bounded and the other left free: **a predicate that enumerates what to strip is weaker than one that says what must be present.**

**ADR-063 — A request schema lives in `packages/shared/src/api/`, and the gate code is minted in `apps/web/lib/`.** `checkInRequestSchema` is in `shared` because mobile posts the same body in Phase 7 and because `shared` already depends on zod — adding a validator to `apps/web` would have been a second one. `newGateCode`/`hashGateCode` could not follow it there: `packages/shared` forbids Node builtins by construction (`shared-not-to-node-core`) and the code is hashed with `node:crypto`. Rejected: hashing in Postgres with `pgcrypto`, which would add an extension to make a Route Handler's job the database's.

*Two things beyond the brief, named so they are not mistaken for scope creep found later.* `POST /api/gate-code` exists because `qr_sessions` stores only a hash, so a code cannot be conjured by a seed row or a SQL insert — without an issuing endpoint the scan half of check-in has nothing to scan and cannot be demonstrated. And `GATE_CODE_TTL_MS` is a constant rather than per-gym configuration because `organization_settings` has no column for it; **it is not the de-duplication window**, which is per gym and must never be given a constant to fall back on.

## Phase 3 decisions (core domain)

**ADR-064 - "Paused" is a condition that is derived, not a status that is flipped.** Approving a pause stamps `membership_pauses.approved_at`; **nothing sets `memberships.status = 'frozen'`, and nothing should.** The implementer found the gap and correctly declined to invent half a mechanism for it.

The obvious repair is a job that flips the status when a pause starts and flips it back when it ends. That needs a scheduler this project does not have, and it creates two representations of one fact which can disagree - a pause row that says paused and a status column that has not caught up yet, or vice versa after a failed run. Instead, **a member is paused when an approved pause covers the date being asked about**: `approved_at is not null and rejected_at is null and <date> between starts_on and ends_on`. NSH-002's consumer is the no-show scan (Phase 4), which is already a per-gym dated query and can ask that question directly. Rejected: flipping the status on approval - a pause may start in the future, so approval and effect are different moments.

**Consequence, stated because it is load-bearing:** `memberships_member_id_live_key` treats `active` and `frozen` as live, and a paused member stays `active`, so a pause does not free the slot for a second membership. That is correct - a paused member has not stopped being a member - but it means `frozen` is currently written by nothing. Phase 5 should either use it or delete it rather than leaving a status the schema offers and the product never sets.

**ADR-065 - `pause_approver_role` may not name a role the matrix forbids from writing pauses.** `organization_settings_pause_approver_role_chk` permits `trainer`; `membership_pauses_tenant_write` is `is_front_office()`, which is `(gym_owner, gym_manager, front_desk)`. A gym that configures a trainer as its pause approver therefore has an approver **RLS refuses to let approve** - the setting and the policy contradict each other, and the setting loses silently. Verified against the live catalogue.

The matrix wins, because it is the security boundary and the setting is a preference. The check constraint narrows to the three roles that can actually write, which turns a silent misconfiguration into a rejected one at the moment somebody tries to save it. Rejected: widening `membership_pauses`' write gate to include trainers - a trainer approving a member's freeze is a commercial decision, and ADR-055's whole argument is that the matrix is not widened to fit a setting.

**ADR-066 - The recurring defect of this project, named so it can be looked for.** Five instances across Phases 2 and 3, each found by a blind reader rather than by the author. The shape is **a privilege boundary crossed for convenience, in a component that runs before the boundary it was meant to respect.** That framing is the visible-suite author's, and it is better than the one this ADR started with ("a rule whose correctness is held by a different component"), because it says what to *look for* rather than what to regret: **every `security definer` function and every `before` trigger, checked as a pair.**

The five:

1. **`<t>_member_select` trusted the hook** to never mint a `member_id` claim alongside a staff role. Closed by naming the role in the policy.
2. **`impersonation_sessions_impersonator_write` had no role term**, so a `front_desk` token carrying an impersonation claim could end the session. Closed the same way.
3. **The exactly-once check-in guard was specified as a Route Handler or an RPC.** `attendance` grants `insert` to `authenticated`, so a direct `supabase-js` write bypasses both. Closed by attaching the guard to the table.
4. **`impersonation_sessions_platform_write` gated the caller and not the `actor_user_id` column**, so an admin could create a session attributed to somebody else. Closed with `actor_user_id = auth.uid()`.
5. **`app.enforce_check_in()` was `security definer`**, owned by a `BYPASSRLS` role, and being a `before insert` trigger it ran ahead of the policy. So *any* `authenticated` session could reach four tables past RLS: a member replaying a `qr_session_id` out of their own readable `attendance` row got `expires_at` and `revoked_at` back in an error message, from a table the matrix gives them zero rows of, and `GL014` printed `checkin_dedupe_seconds` from a table they may not read at all. Closed by **deleting `security definer`** - every role that may insert attendance already holds all four reads (`is_front_office()` ⊆ `is_staff()`), so the elevation bought nothing and cost the isolation.

**Neither half of #5 is a defect alone.** Reading past RLS is what `security definer` is for; running before the policy is what `before` triggers do. The pair is the defect, and that is why it survived an implementer, two blind test authors and me until somebody looked at the two facts together.

**The pattern has two directions, and the search that finds one does not find the other.** This refinement is the visible-suite author's, after the sixth instance turned up looking nothing like the fifth.

- **Elevating past a boundary that was already sufficient.** `app.enforce_check_in()` as `security definer`: the policy was correct, and the function was handed rights it did not need, in a component that runs before the policy. **Found by grepping `security definer` against `before` triggers** — a mechanical search, and it is now in `docs/data-model.md` as a rule.
- **Leaving a rule outside a boundary that never claimed it.** `pause_approver_role`: the policy was correct *and complete for what it claimed to govern* — `is_front_office()` really is who may write a pause — and the rule it did not claim lived in a Route Handler the policy could not see. **No grep finds this.** It is found only by reading each policy against the rules its table is supposed to carry, and asking what the policy does *not* say.

Both are a privilege boundary and a rule disagreeing about who enforces what. The first over-reaches; the second under-claims. A review that only runs the mechanical search will keep finding the fifth kind and never the sixth.

**The rule that follows:** a `security definer` function must justify its elevation against *what its callers already hold*, in a comment, at the point of definition. Where the callers already hold every read, invoker is not merely safer - it is the only version that cannot become an oracle. And the fix is deleting a word, never adding a permission check inside the elevated code: that check is a second copy of the policy, and the copy is what goes stale.

**ADR-067 - The seventh and eighth instances, both inside ADR-066's own fix, and a second rule that follows.** `app.enforce_pause_decision()` was written to close instance #6. A blind pgTAP suite written from `openspec/.../pause-decision/spec.md` by an author who had not read it found two more defects in it, and neither is a variation of the first — they are new shapes worth naming.

- **The trigger was `before update` only.** Every check was hung on the *transition* from pending to approved, and an `insert` has no transition: it arrives at the destination. `membership_pauses` grants `insert` to `authenticated` and its write policy is `is_front_office()`, so one statement — self-requested, self-approved, wrong role — met no rule at all. **The generalisation: "on the table, not in a caller" is not finished until it says *which statements*.** A trigger is a boundary with an event list, and an event list is a place a rule can be left outside of, exactly like a caller. `04_contract_meta.sql` had *pinned* the narrow event list with an assertion arguing that widening it would be someone tidying the rule into symmetry — a guard written around the defect, defending it.
- **A decided pause could be re-decided.** The guard read `if new.approved_at is null or old.approved_at is not null then return new;`, written from the spec sentence "apply the approval rules only to a pause that has not already been decided". It does exactly that: it stops applying the rules, **and then allows the write.** A second, equally-qualified manager could overwrite `approved_by_staff_id`, so the record of who authorised money the gym would not collect became the record of whoever wrote last. **The rule: in a `before` trigger, falling out of a branch is a decision to permit.** "Not governed by this rule" and "allowed" are the same statement there, and a spec that says a rule does not apply is never saying the write is fine — it is saying some *other* rule decides, and if no other rule does, the trigger has just authorised it.

Both were found because the spec was written first and the tests were written from the spec by someone who could not see the code — the arrangement ADR-059 says to reserve for rules whose failure is silent. Both of these fail silently.

**ADR-068 - Two more shapes, both found inside ADR-067's fix, and the thing they have in common.** The Phase 3 critic returned NO-GO on the migration written to close ADR-067, and three of its five defects were introduced by that migration. The pattern is not carelessness; it is that each fix moved a rule to a new place without re-asking what the rule was reading.

- **Widening a trigger's event list changes what the guard compares against.** `before update` becoming `before insert or update` forces every `old.` to become `new.`, because OLD is null on an insert — and at that instant a check comparing the caller's input against a **recorded fact** silently becomes a check comparing the caller's input against **the caller's other input**. ADR-067's fix did this to the separation-of-duties rule on freezes: `new.approved_by_staff_id <> new.requested_by_staff_id`. A manager refused on the straight self-approval sent one UPDATE moving `requested_by_staff_id` onto a colleague and approving it, and the record then named an employee who never asked. **The generalisation: a rule of the form "A must differ from B" is a control only if at least one of A and B is outside the writer's reach in that statement.** So the fix is not a better comparison; it is making the requester immutable (restoring the recorded fact) and refusing an insert that arrives already decided (where no recorded fact can exist).
- **Authorization by absence, and a carve-out that tests the claim instead of the session.** `if app.current_staff_id() is null then return new;` reads "if I cannot identify you, you are trusted." It was written for `postgres` and `service_role`; its actual extension is every `authenticated` session whose token carries no `staff_id` — and Phase 2's claim contract mints exactly that for **impersonation**: `app_role = 'gym_owner'`, a `tenant_id`, no `staff_id`. Such a session passed `is_front_office()`, met no pause rule at all, and could rewrite who authorised a freeze. `docs/security.md` says an impersonating token has the gym's reach and not more; it had more than a real owner's. **The rule: a trusted-context carve-out must test the property it means** — "no policy applies to this session" — not a symptom that correlates with it. The predicate is `row_security_active('public.<table>')`: false for the table owner and for any `BYPASSRLS` role, true for an ordinary signed-in one, naming no role at all.

  **The same carve-out had a second failure in the opposite direction, and the blind holdout author found it by accident.** Testing the *claim* meant `postgres` and `service_role` fell OUT of the exemption whenever `request.jwt.claims` happened to be populated — which PostgREST does on every request including a `service_role` one, and which every pgTAP file here does and never clears. So an Edge Function writing a decided pause would have failed in production, and a fixture write after a claim block was judged against a stale identity. It failed closed, surfacing as a `GL020` naming a staff member with nothing to do with the write, which is why nobody had seen it. The author noticed because two assertions went from green to red when an *unrelated, earlier* claim block changed — **a test whose result depends on what ran before it is telling you something about the system, not about the test.** `current_user <> 'authenticated'` was the first fix here and is also wrong, more subtly: it hardcodes a role name that `pg_roles` already knows the answer about.

**And one non-defect worth recording, because the obvious fix was wrong.** The critic's D4 — every check-in rule reachable by UPDATE, since all of them hang on a `before insert` trigger — was first fixed by `revoke update on attendance from authenticated`. Three suites said no: `06_attendance_checkin` asserts that grant under INT-001, and `06_attendance_rls` exercises `set checked_out_at`, because **a check-out is a legitimate later write to a visit that already happened**. Narrowing the write policy to `for insert` fails the same way and additionally destroys the `with check` that refuses moving one's own row to another gym. The answer was to freeze the columns that carry *what the check-in meant* and leave writable the ones that record *what happened afterwards* — with `tenant_id` deliberately left out of the frozen set, because the policy's `with check` already refuses that and a `before` trigger raising first would answer ahead of the policy, which is ADR-066 exactly. **A hole closed by deleting a feature is not closed; the tests are what said so.**

## Known enforcement gaps

Stated plainly so nobody mistakes a documented rule for an enforced one. A blind critic found each of these by testing what the gates actually catch rather than what they claim to.

- **`AGENTS.md` rule #5 (status vocabularies must be Postgres enums) and rule #8 (money as integer paise) have no CI job.** Nothing stops a future session adding `export const MEMBER_STATUSES = [...]` to `constants.ts` — `registry-lint` would only ask that it be registered. ADR-021 and review are the whole defence. If Phase 1 wants these enforced, the check is "no exported array of status-like string literals outside `packages/db`".
- **`supabase/functions/**` is linted, registry-checked, dependency-cruised and duplication-checked, but not typechecked** — `.jscpd.json` lists it, and `depcruise` cruises `supabase` (the parent dir, because dependency-cruiser errors on a path that does not exist yet) with `packages-not-to-apps` extended to cover it. Typecheck there is Deno, not tsc, so no tsconfig can include it; add a `deno check supabase/functions` CI step when ADR-012's first Razorpay webhook lands in Phase 5.
- **`scripts/**/*.test.ts` is run by vitest but typechecked by nothing.**
- **The `process.env` ban is defeated by aliasing.** `const p = process; p.env.SECRET` is not caught; destructuring and computed access are. `no-restricted-properties` matches on the object name, so any rebinding escapes it.
- **`check-escape-hatches` — three bypasses a blind critic proved, now closed:** every knip config filename knip honours (`knip.jsonc`, `.knip.json`, `knip.ts`, `knip.config.mjs`, …), inline `/* eslint <rule>: off */` config comments, and a nested ESLint config file anywhere below the root (which silently replaces the constitutional config for that subtree). `registry-lint` likewise now sees indented, destructured, `export type {}` and `export * as` shapes, and only exempts the framework-mandated names in Next.js route files rather than the whole file. `check-test-immutability` treats `supabase/tests/**` as tests. Each has a test per hole in `scripts/__tests__/`.

Needs a deliberate answer: a one-time seed script gated behind a secret, a `supabase` CLI/SQL runbook step documented in `docs/security.md`, or an invite-only bootstrap endpoint — whichever is chosen must not become a general-purpose backdoor for creating admins later.

- **OPEN-015 (Phase 6 or 7, when a member-facing and trainer-facing UI exists).** The role matrix is **table-granular**, so a role that needs any column of a table gets every column. Two consequences a blind critic measured rather than assumed: a `trainer` reads `memberships.price_paise`, `addon_orders.total_paise`, `plans.price_paise` and `organization_settings.gstin`, because all four tables are `is_staff()` reads; and a `member` reads their gym's `organizations` row entire, including `tier`, `status` and `trial_ends_at` — the platform's commercial relationship with the gym, which is none of the member's business. Neither is a policy bug and neither leaks another tenant. Narrowing them needs column-level privileges or a view per audience, which is a design decision with its own maintenance cost and should be made when there is a screen that needs it, not before. **Do not "fix" this with a fifth gate** — the vocabulary is closed on purpose (ADR-055).

- **OPEN-016 (Phase 4 - Retention engine).** `max_freeze_days_per_year` and `plans.max_freeze_days` are enforced by nothing. Both are read-then-write in application code, which is the same race the check-in guard was built to remove, so only a constraint trigger closes them properly. Neither's period is defined either: "per year" could be the calendar year or the gym's `financial_year_start_month`, and per member or per membership. Phase 3 chose calendar year, per member, and recorded it here rather than in code comments - decide it deliberately when the retention engine needs it.
- **OPEN-017 (Phase 3 or 7).** Calendar streaks take their window as a parameter because **no challenges table exists**. STK-001 names "calendar streak (challenge periods only)" and there is nowhere to store a challenge period, so the computation is correct and unreachable from any screen until one exists.

- **OPEN-018 (Phase 6 — gym onboarding).** A gym with no `organization_settings` row silently gets no check-in de-duplication, no no-show threshold, no renewal offsets and no pause approver. **Zero organizations are in that state today** and nothing in the product creates a gym yet, so it is latent — but two obvious fixes were tried in Phase 3 and both were worse than the gap. Detecting it in the check-in trigger is unsafe: under `security invoker` "no settings row" and "a gym you cannot read" are the same answer, so raising answers a question about another tenant *before* the policy refuses the row (ADR-066's pair, in the fix for something else — two blind holdout assertions caught it). Creating the row from an `after insert` trigger on `organizations` collides with the settings row that `seed.sql` and thirty pgTAP fixtures insert themselves. **The right place is gym onboarding**, which creates both rows in one transaction, and that is Phase 6.

## Open decisions added after the Phase 0 blind critic

- **OPEN-005 — resolved by ADR-030** (CI applies migrations on serial merge to `main`; drift and pgTAP verify after the apply; `AGENTS.md` rule #7, ADR-024 and gate 9 updated together).
- **OPEN-006 (before real gym data lands — around Phase 5).** Split to a separate Supabase test project so the pgTAP suite and integration tests stop sharing a database with production rows. Until then the rollback rule (ADR-030) is the whole protection; once a paying gym's data exists it is not enough.
- **OPEN-007 (Phase 4 — Retention engine).** `pg_cron` tests need committed state — a scheduled job cannot observe rows inside a transaction that rolls back — so they cannot use the `BEGIN … ROLLBACK` pattern ADR-030 mandates. Solve it there: a dedicated schema or project for cron tests, or a cleanup-on-success pattern with the same "never leaves state behind" guarantee stated and enforced.
- **OPEN-008 — resolved by ADR-052** (every foreign key to a tenant-scoped parent is composite; 50 of 88 keys across 23 tables, with `audit_log` exempt because its nullable tenant column would make `match simple` stop enforcing). Original statement kept for the reasoning: **(Phase 2 - Identity & tenancy, before any product code writes these tables).** No foreign key in the schema re-checks the tenant: every FK references its parent's `id` alone, and Postgres runs referential-integrity probes with row security off, so a gym can write a row *into its own tenant* that references another gym's member, staff row, membership or payment. ADR-047 removed every consequence four blind critics could find, by tenant-scoping the constraints that stood behind it, but the write itself is still possible and it produces rows that are junk in one tenant and invisible in the other. The full fix is `unique (tenant_id, id)` on every parent and composite `(tenant_id, <fk>) references parent (tenant_id, id)` on every child - around forty constraints, one migration, no data to rewrite today and a great deal to rewrite once gyms exist. **Do it in Phase 2 or accept it explicitly.** The cheap alternative, if the owner would rather not carry forty composite keys, is a Phase 2 rule that every Route Handler validates parent tenancy before insert - which is a guard that can be forgotten in a code path, exactly what ADR-037 argues privileges beat.
- **OPEN-009 — RESOLVED by ADR-056** (the hook reads the per-table active definition, a trigger deletes `auth.sessions` on deactivation or role change, `jwt_expiry` is 900, and the platform write gate is `super_admin` only so support can no longer promote itself). *Original text:* `platform_users.is_active` and `staff.is_active` are written by nothing and read by nothing. `app.is_platform()` reads only the `app_role` JWT claim, so deactivating a compromised super admin does not revoke their live token - and while it lives they retain `for all` on `platform_users` and can set their own row back. Phase 2's access-token hook must read `is_active`, and must decide the session-revocation story (short expiry, a `session_id` check against `auth.sessions`, or both). Related, and in the same hands: `platform_support` and `super_admin` are indistinguishable to every Phase 1 policy, so a `platform_support` session can promote itself by updating `platform_users`. That is ADR-032's deferral of the role matrix working as intended, and it must not be inherited silently.
- **OPEN-010 (Phase 3 - Core domain).** Two integrity rules Phase 1 cannot express and Phase 3's write paths must own. `consents.recorded_at` is client-writable on an append-only table whose read model is "latest row per (member, purpose)", so a row stamped far in the future is latest forever and a later genuine withdrawal never takes effect (DPD-004); `check (recorded_at <= now())` is rejected as non-immutable, so the consent writer must stamp it server-side. And `notifications.dedupe_key` is unconstrained `text`, so PAY-002's "at most one message per stage" holds only as far as the sender composes a deterministic key - fold a run id or a timestamp into it and the unique index never fires. The precedent for constraining it in the schema is `audit_log_action_format_chk`, which exists precisely because the format carries the meaning.
- **OPEN-011 (contract-wide, whenever the next `spec:` change touches it).** Every "not empty" check in the schema is `<> ''`, which a single space satisfies - including `attendance_corrections.reason`, where DQA-003 says a correction without a reason must be *impossible*, and `membership_pauses.reason`, `refunds.reason`, `impersonation_sessions.reason`, `consents.version` and `consents.source`. `btrim(x) <> ''` is the strictly stronger form. Not changed here because it touches every cluster including three already applied, and because it is a uniform contract decision rather than a per-table one.
- **OPEN-014 (whenever the pgTAP harness is next touched).** The "no JWT claim at all" branch of `app.current_tenant_id()` is **not exercised anywhere in CI**, and the suite should not be read as though it were. A missing claim has two shapes — the GUC set to the empty string, and the GUC never set in the session — and `docs/data-model.md` requires both to yield null and zero rows without raising. Only the first is reachable: a custom GUC placeholder, once assigned, reverts to the empty string rather than to undefined, `reset` and `set … to default` both land on the empty string, and `DISCARD ALL` — the one statement that would restore the unset state — cannot run inside a transaction block, which every pgTAP file is by ADR-030. One holdout file used to cover the unset branch by accident, because it drew a fresh backend when the suite ran as separate invocations; ADR-051 collapsed those back to one and the accident ended. Both branches are fail-closed in the accessor's implementation, so this is missing coverage rather than a known hole. **The fix, if it is wanted, is a CI decision and not a test-file one**: run one file in its own invocation so it gets a fresh connection. Recorded rather than quietly lost, because the alternative is a suite that looks like it covers a branch it does not.
- **OPEN-012 (Phase 5 — Money).** Invoice arithmetic is unconstrained and unspecified: `total_paise` is unrelated to `taxable_paise + cgst + sgst + igst`, CGST/SGST and IGST are not mutually exclusive, `cgst_paise = sgst_paise` is not enforced, a refund may exceed the payment it refunds, and a discount may exceed the price. No requirement in any Phase 1 spec states these rules, so this is a specification hole rather than a missed implementation — recorded rather than archived in silence, on the blind final critic's finding. Phase 5 either writes the checks or states why the arithmetic is the application's to own.
- **OPEN-013 — RESOLVED by ADR-055** (a 36-row role matrix, read and write as separate policies, and a member-scoped read policy on the fourteen tables a member may see). *Original text:* There is no intra-tenant authorization. Every tenant policy is `tenant_id = app.current_tenant_id()` and nothing more, so any `authenticated` session carrying a gym's `tenant_id` can read and write **every row in that gym** — every other member's phone number, every payment, `staff.role`, `razorpay_accounts`. That is a deliberate Phase 2 deferral (`docs/data-model.md` says the role matrix lands there) and no Phase 1 spec promises otherwise, but `member` is already an `app_role` label and no open item said out loud that the current default is full-gym access. It is DPDP-relevant: a member session under this shape can read the whole gym's personal data. Phase 2 must confront it before it issues a member token, not after.

## Taken without the product owner during the Phase 1 overnight run — confirm or reverse

The owner authorised the Phase 1 run end to end and was asleep for it, with a standing instruction: where a decision is genuinely the owner's, pick the safest default, record it, and carry on. Each of these is that. None is load-bearing enough that reversing it later costs more than one migration or one commit, and each names what reversing it would take.

- **Roles move to the database (ADR-031).** `ROLES`/`Role` deleted from `packages/shared`; `app_role` is the enum. Reverse cost: re-adding a constant and a registry row — but then two vocabularies exist again.
- **Claim names `tenant_id` and `app_role`; accessors in a private `app` schema (ADR-032).** Phase 2's access-token hook must set exactly these two claim names, or every policy in the schema silently matches nothing. Reverse cost: one migration replacing two function bodies, before Phase 2 ships the hook. **This is the decision with the shortest window to change cheaply.**
- **Two tables outside tenant scoping (ADR-033).** `platform_users`, `audit_log`. Reverse cost: a migration, plus special-casing a synthetic platform tenant in every isolation test.
- **The seed is a manually dispatched workflow, not a migration and not a session command (ADR-034).** Reverse cost: none, it is one workflow file.
- **UUID v4 primary keys (ADR-035).** Reverse cost: high once data exists — this is the one to disagree with early if at all.
- **DPD-007 split: retention policy now, breach runbook in Phase 8 (ADR-036).** Reverse cost: none, it is a doc.
- **Calendar-day defaults move off `current_date` to IST-local (ADR-039).** A contract change, so a `spec:` commit. Reverse cost: one migration per affected column, and reversing reintroduces a five-and-a-half-hour window each day in which a date is wrong.
- **The check-constraint rule word is now fixed (ADR-040).** Reverse cost: none, it is a naming convention — but it must be fixed *before* the fan-out, not after.
- **The per-table privilege contract, and no `force row level security` (ADR-037).** Previously decided and written into `docs/data-model.md` with no ADR number; the `pg_default_acl` finding behind it was re-verified against Cloud in this run before numbering it. Reverse cost: a migration per table, and a signed-in user regains `delete` and `truncate` on everything.
- **Tests and implementation land as two commits in one push, with the red pgTAP run taken once on the contract cluster (ADR-038).** Reverse cost: none going forward, but a cluster already landed cannot be re-run red.
- **A `member_devices` table was added to the `comms` cluster, which the in-flight table list did not have.** ADR-016 makes push notifications v1's primary channel, and a `notifications` row with no device token to deliver to is a dead end; the alternative was a Phase 3 migration to add it. It is deliberately minimal — member, platform, push token, last-seen, active flag — and carries no delivery-receipt state, which belongs on `notifications`. Reverse cost: dropping one table before any code reads it. *The first attempt at this recorded the decision here and in `docs/security.md`'s retention table and the `comms` EARS spec, but never added the table to `docs/data-model.md`'s table list — so the cluster agent implementing `comms` would have had a requirement with no table to build. Caught on the resumed run's critical read of the in-flight work; the table list now carries it.*
- **The contract was drafted by the orchestrator's sub-agent and reviewed by the orchestrator, then by a fresh-context blind critic**, rather than by a second independent author. The property that matters — the contract is fixed and independently checked before any fan-out — holds either way.
