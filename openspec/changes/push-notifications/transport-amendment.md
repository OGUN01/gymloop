# NTF transport amendment — PROPOSED OWNER DECISION REQUIRED

Status: **proposed, 2026-10-03; not approved, frozen, implemented, deployed or live**. This document prepares one narrow architecture decision for `proposal.md`. It authorizes no extension enablement, secret creation/provisioning, Firebase signup/configuration, deployment or phone action. Tests, holdouts and implementation have not been changed for this amendment.

## Decision proposed

Permit one separate Supabase Edge Function, `supabase/functions/push-dispatch/index.ts`, solely for Android FCM HTTP v1 provider I/O. Keep due-event creation, tenant selection, eligibility, consent, category preferences, source validity, reservations, budgets and notification transitions in SQL. Keep all member/staff mutations in caller-scoped Next Route Handlers. Do not extend `no-show-scan`, the media function, or a web admin client into a push worker.

This is an explicit exception to `docs/architecture.md`'s Edge boundary and ADR-012, alongside the separately approved media exception. It narrowly amends ADR-077 to allow SQL-scheduled HTTP wakeup for provider I/O that PostgreSQL does not perform itself; `pg_cron` remains the scheduler. The no-show scan remains SQL-scheduled and its Edge entry point remains an operator's manual rerun.

Owner decision: approve this boundary and its proposed infrastructure/custody plan for incorporation into the future frozen NTF contract, or name an alternative transport. Approval of the design alone does not provision or enable it. The separately named Firebase/app prerequisite below still must be supplied before protected provisioning and live acceptance.

## Fixed transport boundary

`POST /functions/v1/push-dispatch` accepts exactly an empty JSON object. It accepts only a dedicated high-entropy `PUSH_DISPATCH_SECRET` through `x-gymloop-push-dispatch-secret`, verified before database access or provider I/O. This credential permits wakeup only; it is neither a member JWT nor a Supabase service key and grants no direct database access. Do not reuse the operator's `CRON_SECRET`, accept ordinary Auth tokens as authorization, or accept tenant/member/device/token/campaign/payload/URL parameters. Other methods, extra fields and missing/invalid credentials fail closed, with no dispatch. Responses contain bounded count-only operational facts; no recipient ids, tokens, reservations, provider ids, credentials or upstream body. No browser CORS or public health operation is added.

The proposed custom-secret endpoint requires `verify_jwt=false` for this function only, because its wakeup credential is not a JWT. The handler must therefore authenticate every request itself; disabling the platform JWT check is never permission to run anonymously. Supabase documents this responsibility for custom-authenticated functions in [Securing Edge Functions](https://supabase.com/docs/guides/functions/auth). The exact comparison, input limits and HTTP errors are frozen and independently tested before implementation.

The adapter may only authenticate wakeup, validate required configuration, obtain short-lived OAuth access credentials, obtain SQL-authorized work, send the fixed generic FCM message, classify documented provider responses and submit factual results. It never computes an audience, overrides authorization, chooses recipients from the request, writes delivery tables directly, sends paid messages, or marks receipt/click/conversion. It sends only to the FCM endpoint for the configured approved Firebase project; no request-supplied host or redirect is followed. Provider configuration/authentication failure stops further dispatch rather than silently consuming a queue or invalidating tokens.

## Reachable SQL facade, private rules

`app` remains outside PostgREST: current `supabase/config.toml` exposes only `public` and `graphql_public`. An Edge request cannot call the draft's `app.reserve_push_attempts` or `app.finish_push_attempt` as REST RPCs. Do not expose `app` to solve that problem.

Add only these proposed service-only `public` facades, with private SQL bodies/helpers behind them:

| Proposed facade | Sole responsibility |
|---|---|
| `public.reserve_push_attempts` | Select bounded due work across SQL-selected eligible tenants, serialize each tenant's budget and create durable reservations; return reservation identifiers without recipient tokens. No caller-supplied tenant or recipient selection. |
| `public.authorize_push_attempt` | Given only an existing attempt/reservation pair, freshly validate current account/member/guardian binding, exact device revision, preference, latest purpose consent, source/version and quiet-hour eligibility immediately before that individual provider request. Return only the fixed authorized token/message projection and dispatch expiry, or a refused/deferred result. |
| `public.finish_push_attempt` | Given the same pair and bounded provider facts, record known acceptance, explicit failure or uncertainty, enforce exact-result replay/conflict, and invoke only the legal canonical notification edges. It cannot invent receipt. |

These names describe the concrete proposed boundary, not registered or implemented exports. Final signatures, return shapes, bounds and errors remain a serial freeze prerequisite. A separate authorization step is necessary because eligibility at batch reservation can become stale while earlier devices are sent. The adapter must not send if authorization expires, fails or has an unknown outcome. A fresh authorization is a database decision immediately before I/O, not a claim that withdrawal and FCM are one atomic transaction.

Each facade checks credential-only service context, has an empty search path and explicit ownership/privilege design. Revoke EXECUTE by name from PUBLIC, `anon` and `authenticated`; grant only `service_role` for the transport facade. Verify effective privileges with `has_function_privilege`, including every ordinary/platform/impersonation role, rather than trusting migration comments (ADR-074). Private cron work runs under the existing trusted `postgres` job context; no ordinary caller can start it. Freeze whether each facade is invoker or narrowly justified definer with its exact underlying grants; neither an invoker label nor a service key may bypass the notification evidence invariants. No general table-write shortcut is introduced.

The existing runtime-provided Supabase service credential stays inside `push-dispatch`, used only for these facade calls. Web/member/staff request paths receive no admin client. PostgreSQL trusts that credential for the adapter's provider evidence, as it already trusts credential-service boundaries; it cannot independently prove that FCM accepted a message. A compromised service credential remains an infrastructure trust risk, not cryptographic provider attestation.

## SQL schedule and scoped automated wakeup

Propose one named `pg_cron` job, `push-dispatch-minute`, every minute. A private SQL driver derives tenants, runs bounded due-event creation through the proposed `app.run_push_events`, then issues one `net.http_post` wakeup to the fixed Gymloop endpoint with `{}`. The HTTP wakeup does not reserve attempts or carry recipients. Repeated/overlapping wakeups must remain safe through database reservation/dedupe/budget rules; wakeup success proves only invocation, never a member send. Event creation and inbox availability continue without a functioning provider. The worker performs bounded work per invocation; later cron ticks drain remaining work, without an unbounded Edge loop or self-rescheduling service.

Supabase's official [Scheduling Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions) documents `pg_cron` plus `pg_net` for periodic Edge invocation and recommends Vault for the invocation credential. Repository migrations already declare `pg_cron` in `20260909170000_the_critic_was_right_four_times.sql`; searches found no `pg_net` or Vault extension declaration. Existing Vault-id columns do not prove an installed extension or configured secret. No Cloud state was queried. `pg_net` and Vault must therefore be treated as proposed infrastructure prerequisites, not existing provisioned capability.

If approved later, CI-applied forward-only migrations declare the required supported extensions and private scheduling objects; protected provisioning supplies the wakeup credential before the job is enabled. Store the dedicated credential under proposed Vault name `gymloop_push_dispatch_secret`. The endpoint is fixed to project `pecxrpskmfeuyzngvewq`, not looked up from request data. Cron text refers to a private helper and Vault name, never a literal secret. Missing secret/configuration leaves wakeup disabled or refused with observable operational failure; it must not fall back to the service key, publishable key or a dummy value. The scheduler is enabled only after the exact deployment and configuration checks pass. SQL-only jobs do not acquire this dependency.

Vault encrypts stored secrets but exposes decrypted values to authorized SQL through its view; [Vault documentation](https://supabase.com/docs/guides/database/vault) supports that distinction. Freeze explicit denial of ordinary-role Vault access and of networking queue/header inspection: [pg_net documentation](https://supabase.com/docs/guides/database/extensions/pg_net) describes queued headers and default ordinary-role object access, even though `net` is outside the Data API. Do not claim Vault encrypts every transient HTTP header. The unlogged HTTP queue can lose wakeups on a crash; later cron ticks retry wakeup, while durable SQL attempts govern whether a provider request is allowed. Protected operators/SQL owners remain privileged custodians; no request headers or decrypted values enter logs, receipts, artifacts or audit.

## Custody, rotation and protected CI

Proposed names are `PUSH_DISPATCH_SECRET`, `FCM_PROJECT_ID` and `FCM_SERVICE_ACCOUNT_JSON`. They do not claim existing values. Dedicated wakeup secret: owner-controlled protected GitHub environment secret, matching Edge secret, and matching restricted Vault entry only. Firebase server credential: protected GitHub environment secret and Edge secret only; never Vault, Vercel, mobile, browser, repository, migration, test fixture or build artifact. The service account must be restricted to FCM sending for the named approved Firebase project; its private key obtains short-lived OAuth access tokens in the trusted adapter, following [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api). Android Firebase registration/configuration is a separate client prerequisite and contains no server private key.

Provisioning/deployment is proposed through a dedicated protected CI job targeting only `pecxrpskmfeuyzngvewq` with the correctly authenticated Supabase CLI. It requires protected owner-controlled environment access, exact commit identity, passing SQL authorization/invariant gates and Deno checks, completed preceding DB workflows, then secret provisioning and exact `push-dispatch` deployment. Enable the job last. `.github/workflows/functions.yml` currently typechecks and deploys only `no-show-scan` on path-filtered main pushes; it has no protected environment or push-secret provisioning. Do not describe that current workflow as an existing protected push deployer. Freeze and review its narrow extension or dedicated replacement job before granting access. Neither drafting nor design approval triggers a deployment.

Rotation is an explicit protected operation: pause wakeups and new dispatch, drain/expire outstanding reservations under the frozen unknown-outcome policy, replace the Edge/Vault wakeup value, verify old-value denial and new-value acceptance without recipient sends, then resume. Never accept both indefinitely. For Firebase key rotation, pause new dispatch, provision the approved replacement, verify OAuth/project binding, revoke the retired key and discard cached access tokens before resuming; already-issued token validity must be accounted for. Suspected compromise stops dispatch first. Record only names, versions/timestamps and verification outcomes, never secret values. Supabase service-key rotation remains the existing platform-wide process. All `process.env` reads remain in `config/env.ts`; freeze the Edge/Deno configuration accessor explicitly under the existing platform-free boundary rather than copying historical direct-read exceptions without review. Register every eventual export/env/constant before implementation.

## Retained contract and delivery truth

Latest service consent for external transactional push follows current INT-002, DPD-004 and `app.notification_consent_purpose`; promotional purpose consent remains independently controlled. ANC/CLS approved transactional in-app display rules do not grant external push consent. Promotional dispatch remains barred in `[21:00,08:00)` Asia/Kolkata, with next-opening deferral and fresh checks; transactional categories retain their exemption. Preserve source-feature gym-local/frozen-day semantics and immutable `scheduled_for`, content, identity and dedupe facts. Adapter time never rewrites the source day. These are retained rules, not additional owner confirmation requests. Any deliberate deviation would be a separate contract amendment.

FCM acceptance and a returned message name support “Accepted by push service” only. “Received in app” and “Opened” require the separately validated authenticated callback/open evidence. Lost responses or expired started reservations remain “Delivery unknown”; no blind resend, inferred delivery, manufactured ANC read, or exact-once receipt promise. Quiet-hour dispatch and TTL are best effort against later OS display, not a guarantee against late display. Missing provider configuration retains `provider_unconfigured` behavior and the real inbox/feed.
