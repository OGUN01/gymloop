## Purpose and bar

Make important membership/class updates reach Android without pretending that a phone received a message merely because a provider accepted it. The real member inbox and ANC Home feed remain available when permission is denied, the app is killed or push fails. Public comparable and measurable bar: [Linear notification settings](https://linear.app/docs/notifications), evaluated in `docs/design/v2/ntf-bar.md`.

In scope: member Android FCM HTTP v1, current consent and category preferences, device binding/rotation, deduped renewal and away-case alerts, CLS reminders and existing class notices, reviewed ANC broadcasts, safe open/receipt acknowledgements, staff reach/failure reporting. No charge or wallet movement. Out: browser/iOS push, Expo Push Service, WhatsApp, payment/desk alerts (PAY later needs a separately approved staff-device contract), new segmentation engine, new inbox state machine, scheduled announcement publication, automatic ANC edit blasts, arbitrary custom campaigns, receipt/read percentages inferred from FCM acceptance.

## Smallest proposed wireup and owner decisions

Native uses SDK-compatible `expo-notifications`, Android channel creation, contextual permission request, `getDevicePushTokenAsync` for the native FCM token and token/response listeners. The current package has no notifications dependency; add only during implementation. No Expo token masquerading as FCM token. Provider requests use direct FCM HTTP v1 with server-only short-lived OAuth credentials; no legacy server-key API or client service-account key. [Expo direct delivery](https://docs.expo.dev/push-notifications/sending-notifications-custom/) and [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api) support this choice.

Proposed transport: SQL `pg_cron` owns due-event creation/eligibility scheduling, and a narrowly authenticated existing operator-job Edge transport performs provider I/O and service-only finish RPCs. It must carry no public member mutation logic; web mutations stay Next Route Handlers. Automated wakeup needs a scoped dispatch credential and an approved HTTP scheduling transport. **Architecture currently excludes extra Edge application logic; the proposed FCM adapter/wakeup is an OWNER-GATED architecture amendment, not implicit authorization.** Do not create a new Edge service, HTTP scheduler, DB extension, secret or production worker before that amendment. Alternative transport can change before freeze, but has to retain the exact SQL authorization/evidence contract.

Open owner decisions (must settle before freeze):

1. Exact existing/approved Firebase project, Android application registration/configuration and protected server credential custody; public Firebase signup/provider configuration are owner-gated. No recreation or purchase.
2. Approve the minimal adapter/scheduler boundary above (including secret custody/rotation and protected CI deployment), or name another approved transport. The draft does not authorize web admin clients.
3. Confirm external transactional pushes require latest `service` consent, matching INT-002/DPD-004 and current `notification_consent_purpose`; ANC/CLS transactional **in-app** display retains its approved bypass. Safety/closure push without service consent would be a deliberate contract change requiring explicit approval.
4. Confirm quiet hours mean no promotional **dispatch** in `[21:00,08:00)` Asia/Kolkata. FCM/device scheduling cannot guarantee an accepted push will never display late; TTL expires by the next 21:00 and copy promises best effort only. A literal guarantee against late OS display is incompatible with background OS notifications and requires a different product choice.

Delegated proposed mechanical choices (reviewable defaults, not additional owner blockers): one reviewed campaign per ANC version; owner/manager reviews, desk previews only; preferences keyed by existing DB category; no automatic blast on an ANC edit; reminders 60 minutes before a booked class; away alert once per current no-show case at at least 7 completed eligible absence days using existing attendance/holiday/scoring rules; no backfill of old events on enabling the provider. Proposed caps: 1 reviewed bulk campaign per tenant per hour, 1,000 target members per campaign, 100 provider device requests per tenant per minute, 100 rows per worker batch, 90 seconds per transport reservation, 30-day dormant-token cutoff (refresh on authenticated app activity), and existing 1-year device-token hard pruning rule. Named constants below hold numbers; final freeze must pin exact validation/bounds, SQLSTATE allocation and scheduler grant/wakeup details.

## EARS draft

- **NTF-001 (source of truth).** WHEN an eligible event exists THE SYSTEM SHALL make its real inbox/feed content available independently of permission, token, category push preference or provider result; no push failure SHALL erase an inbox row or ANC card. Consent for promotional content remains the source feature's current predicate. External transactional push requires current service consent under the proposed decision.
- **NTF-002 (categories).** WHEN a verified member changes a category preference THE SYSTEM SHALL alter only that member's push preference and audit an actual change. `renewal`, `payment`, `fulfilment`, `promotion`, `motivation`, `class_update`, `announcement` derive from Postgres. Absence alert uses `motivation`; existing motivation opt-out remains an additional veto. Preferences never grant consent or disable operational in-app history.
- **NTF-003 (identity).** WHEN Android registers/rotates a token THE SYSTEM SHALL bind it only to complete current member+tenant+user claims and the matching active member row. A known minor SHALL require a complete guardian record and guardian-linked account; otherwise no push. Handover, unlink/rebind, disabled account, blocked/cancelled/erased member or stale registered user SHALL prevent sends and receipt writes. No contact-based cross-account routing.
- **NTF-004 (rotation/staleness).** WHEN token rotation, explicit unregister, confirmed FCM `UNREGISTERED` or confirmed token-specific invalidity occurs THE SYSTEM SHALL deactivate only the exact device revision. A late error for an old revision SHALL NOT disable its replacement. Generic `INVALID_ARGUMENT`, auth, quota or provider outage SHALL NOT invalidate tokens. Dormant devices SHALL be excluded under the frozen cutoff and token values blanked under existing retention/erasure rules. [FCM token guidance](https://firebase.google.com/docs/cloud-messaging/manage-tokens).
- **NTF-005 (current eligibility).** WHEN a provider request is authorized THE SYSTEM SHALL recheck current organization/member/account/device eligibility, preference, latest consent and source event validity. ANC SHALL call `app.announcement_audience` and match live current version; class reminders require still-booked future scheduled session and live membership; renewal uses existing current-cycle/remainder predicate; absence requires current eligible open no-show case and GRD scoring gate. Consent withdrawal committed before authorization SHALL produce zero provider requests. Withdrawal after the external request began cannot recall it; never claim atomic database/FCM cancellation.
- **NTF-006 (quiet hours).** WHILE IST time is at/after 21:00 or before 08:00 THE SYSTEM SHALL reserve/send no promotion-category request, defer it to next 08:00 without altering frozen `scheduled_for`, and revalidate at that time. Transactional categories are exempt. Promotional FCM TTL SHALL not extend beyond the next 21:00; late OS display remains best-effort and disclosed.
- **NTF-007 (event dedupe).** WHEN a scheduler/backfill/campaign repeats THE SYSTEM SHALL retain one notification per existing tenant event key and one provider request per notification/device revision reservation. Existing renewal and CLS source keys SHALL remain unchanged; push children of existing in-app events use `push:<source_notification_id>` with `source_notification_id`, never rewrite the source. ANC uses its exact approved key. New class reminders use `class-reminder:<session_id>:<member_id>` and new absence events `absence:<no_show_case_id>:<member_id>`; source inbox keys use these and push children use the common prefix. No retroactive send of pre-enable events.
- **NTF-008 (honest uncertainty).** WHEN FCM explicitly accepts a request THE SYSTEM SHALL record `provider_message_id` and permit `scheduled→sent` only through the guarded service path; staff copy SHALL say “Accepted by push service”. WHEN a response is lost or a started reservation expires without a recorded result THE SYSTEM SHALL record “Delivery unknown”, suppress automatic resend for that device/event and never infer accepted/delivered. Multi-device facts SHALL remain per attempt; one accepted device makes the notification sent, zero acceptance after all terminal facts makes it failed (uncertainty reason when applicable). Known failures on one device SHALL not downgrade a notification already acknowledged on another.
- **NTF-009 (receipt truth).** WHEN the authenticated app observes a received callback or opened OS response for an accepted matching attempt THE SYSTEM SHALL record receipt evidence through NTF's narrow command, never from provider acceptance, analytics estimates or screen-list rendering. Open implies device receipt and may legally traverse both existing edges. “Delivered” SHALL be presented as “Received in app”; absent evidence SHALL remain unknown. Offline callbacks may retry idempotently after authentication, storing only ids/revision/event, and account change SHALL discard them. `converted_at` is untouched. [FCM delivery reporting](https://firebase.google.com/docs/cloud-messaging/understand-delivery).
- **NTF-010 (safe opens).** WHEN an OS response is opened THE SYSTEM SHALL validate ids, current identity and current RLS source exposure and route through a closed allowlist to member inbox, membership, class detail or live ANC card. No arbitrary URL, external intent, tenant selection, payment action or mutation SHALL run from payload. Signed-out opens wait for login and then revalidate; stale/foreign/expired source displays “That update isn't available.” No ANC read marker until the card is actually opened.
- **NTF-011 (review/limits).** WHEN a bulk ANC push is requested THE SYSTEM SHALL require real owner/manager review of title, kind, current version, eligible count and quiet-hours notice; front desk may preview but never review/send, trainer/member/platform/impersonation may not review. A new ANC version needs a new explicit review. Tenant serialization SHALL enforce frozen campaign and request limits under concurrent workers, no cross-tenant budget or audience. Review is permission to attempt, never evidence of receipt.
- **NTF-012 (zero charge).** WHEN any push event is processed THE SYSTEM SHALL write zero wallet/ledger/payment changes and never call `accept_paid_notification`; amounts in existing renewal inbox content retain integer-paise formatting while lock-screen push contains no amount or arrears.
- **NTF-013 (privacy/isolation).** THE SYSTEM SHALL expose no device token, guardian address, consent history, detailed financial/absence information or other member data in OS payloads, campaign aggregates, errors or audit. Lock screen title is the business name and body “You have an update. Open the app to view it.” Data carries validated notification/source identifiers only. All writes/reads SHALL bind tenant claims and deny foreign targets identically to unknown targets.
- **NTF-014 (audit/retention).** WHEN an actual preference/device/review/cancel change occurs THE SYSTEM SHALL audit actor, tenant, row ids, category/enabled or token revision/active flags and count-only campaign facts; no token, key, contact or payload. Existing notification edge audits remain the sole delivery business audit. Preferences: last membership end +3 years, delete on erasure; campaign review: account closure +8 years, hold without member identifiers; attempts: send/start +1 year, blank provider ids on erasure; existing notifications +1 year blank and devices 3 years blank/1-year inactive pruning remain authoritative. No deletion of consent proof. Retention jobs must integrate existing erasure/pruning paths; no claim of policy enforcement by documentation alone.
- **NTF-015 (configuration failure).** WHERE provider configuration is missing THE SYSTEM SHALL display “Push isn't configured. Updates remain in the app.” and retain existing `provider_unconfigured` behavior; no test stub SHALL become a live delivery result. Provider credential failures SHALL stop dispatch, surface a staff actionable error and retain inbox content.
- **NTF-016 (surfaces/accessibility).** THE SYSTEM SHALL provide native You→Notifications permission/current-device/category settings, web member category settings plus inbox (web push explicitly unavailable), and console Messages campaign review/status, using existing Chalkline components, light/dark, large text, accessible toggles and loading/empty/error/offline states. Permission prompts SHALL follow a member action; denied permission opens OS settings only on request. No extra navigation tab.

## Reservation and evidence invariants to freeze

Use row locks plus per-tenant budget serialization. Start a durable attempt before provider I/O, validate again immediately before dispatch, record a known provider result through service-only finish, and never blindly retry after network uncertainty. Queue delay is an attempt eligibility timestamp, not a mutation to frozen notification schedule/content. Crash before/after request must be distinguishable where evidence permits; when it does not, prefer one potentially missed push to a duplicate buzz and keep the inbox. A device's known explicit retryable rejection may be retried only if the frozen contract defines its attempt bookkeeping and backoff; the smallest initial default is no automatic provider retries. FCM offers no app event idempotency guarantee, so “exactly once received” is never promised. Client receipt has user/device attestation, not cryptographic proof of physical display.

Existing `app.enforce_notification` must admit a push acceptance only when the current service-owned accepted attempt exists, and push receipt/click only through the named validated definer; direct staff/service table writes lacking evidence fail. Keep the canonical graph unchanged. Revise `send_notification` only to authorize queueing under reviewed/source rules; it must never write sent merely by queueing. Frozen spec must pin its backward-compatible result and provider-unconfigured path before any test author works.
