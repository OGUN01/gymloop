# Services, classes and booking (CLS-001…CLS-040)

Feature F2 of `docs/planning/v2-feature-map.md`, phase V2-B4 of `docs/planning/v2-campaign-goal.md`, batch 2 of
`openspec/changes/v2-batch2-shared/shared.md` (which wins wherever the two disagree). This change **owns shared
primitive 2 (BOOKING)** — the lock, the `booking_status` vocabulary, the cancel-window setting and the
`GL090…GL096` refusals — and writes the in-app notices of shared primitive 3.
Rigor: **full blind arrangement (ADR-059)** for the RLS read policies, the capacity and booking state machine, and
the two cancel paths (member cancel; session cancel with notices) — a silent mistake there overbooks a class, shows
one member another member's identity, or tells nobody that a class is off. **Relaxed** (one implementer, spec-first
and tests-first, every gate unchanged) for catalogue and timetable CRUD and for every screen.

## Why

The core engine records who showed up and who stopped. A business that sells *classes* (Zumba, yoga, HIIT, dance
batches, martial arts) needs the member to see what is running, reserve a place, and be told when it is off — and
needs the desk to see who is coming to the 6 pm batch. That is the front of the member app (feature map, Wave B).
This change adds the per-gym service catalogue, the weekly timetable with trainer and capacity, concrete dated
sessions, and booking with a capacity lock, a live-membership gate, a per-gym cancellation window, and a transactional
notice when the gym cancels. It does **not** change what attendance means: a booking is a promise, attendance stays the
check-in record (ATT, NSH, STK unchanged).

## Scope

In: DB (4 tables, 2 enums, 1 enum value, 2 settings columns, helpers, 14 definer commands and reads, 2 invoker reads, a
daily generator job), shared contracts, web (member Classes page, desk Classes pages, owner catalogue and schedule
editor, 14 API routes), mobile (member Classes tab, desk Classes tab), audit, docs. Out (recorded, not built):
waitlists and trial-class booking by leads (F15 — hooks only); automated reminders and push (NTF); paying for a class
or class packs (PAY); recurring "book every Monday"; desk override of capacity or membership; rescheduling a session
that has bookings; bulk "cancel all upcoming sessions of a service"; a per-gym advance-booking window other than the
fixed generation horizon; overlapping-booking refusal for one member; releasing a member's future bookings when they
are erased (the DPD-006 routine does not exist yet — the desk cancels them, and the roster flags the member); route-level
rate limiting of booking calls (gate 24 has no infrastructure yet); iCal export; guest passes. OCC's fill-rate
analytics are not built, but every fact they need is stored (see CLS-039).

## Design decisions and deliberate deviations (ADR-183 has the reasoning)

- **D1 Materialized sessions.** A weekly rule produces concrete `class_sessions` rows over a rolling 28-day horizon, by a definer generator (run by every rule command and by a daily job). Bookings reference a session row; per-occurrence facts (cancelled, capacity, trainer) live on it.
- **D2 Rule identity is immutable.** Weekday, local start time, service and branch of a rule never change; to move a class, end the rule (`valid_until`) and create a new one. Capacity, trainer, duration, end date and active flag are editable and propagate (CLS-005).
- **D3 Freeze-and-finish, never silent cancellation.** The system never cancels a session that has bookings on its own — not for a disabled service, an ended rule, a holiday added later, or a deactivated trainer. Those sessions stand and run; only an explicit owner or manager action cancels, and that action notifies. Derived sessions that nobody has booked are the only rows the system removes.
- **D4 One booking row per (session, member).** Cancelling then re-booking revives the row (history is in the audit log). Capacity counts the *holding* statuses `booked`, `attended`, `no_show`.
- **D5 A booking is not attendance, and nothing infers it.** `attended` / `no_show` are set only by explicit desk (or assigned-trainer) marking, audited. No trigger on `attendance`, no sweeper that turns unmarked bookings into absences.
- **D6 Members read through definer RPCs only.** No member policy exists on any of the four tables (deviation from "readable by members of the same tenant (and branch)": the same visibility is delivered with the branch filter, the disabled-service filter, the trainer's display name only, and counts only — none of which a row policy can express). Staff read the tables directly; the roster is readable by every staff role (no fifth gate).
- **D7 Booking's membership test mirrors check-in exactly** (status `active` or `frozen`, dates inclusive, null dates open), evaluated on the session's local day, with a parity test against `app.enforce_check_in`'s predicate.
- **D8 Cross-branch booking is refused by default**, with a per-gym setting `class_allow_cross_branch`.
- **D9 CLS-only refusal codes live in a new block `GL110…GL114`** (the shared block `GL090…GL099` is left whole for booking-family refusals).
- **D10 Trainer overlap is advisory.** GL096 is a PT-slot refusal and is never raised here; the timetable read flags `trainer_overlaps` instead.

**RLS and grants.** On each of the four tables exactly two policies, tenant term first, as the `04_contract_meta` matrix pins them: `<table>_tenant_select` (`for select to authenticated using (tenant_id = (select app.current_tenant_id()) and (select app.is_staff()))`) and `<table>_platform_select` (`using ((select app.is_platform()))`). No write policy, no member policy, no `_all`. Grants: `revoke all on public.<table> from anon, authenticated; grant select on public.<table> to authenticated;` — `authenticated` holds no insert, update or delete on any of them; `service_role` keeps its defaults (the generator job). Matrix rows added to `04_contract_meta`: `('services','is_staff',null,null)`, `('class_rules','is_staff',null,null)`, `('class_sessions','is_staff',null,null)`, `('class_bookings','is_staff',null,null)`. **No `*_preview_read_only` trigger**: the tables hold no DML grant for `authenticated` and every writer is a definer command whose actor helper refuses an impersonation claim (CLS-024).

**Triggers** (one per table, all in the universal `<table>_touch_updated_at` slot, all security invoker with an empty search path): `services_touch_updated_at` → `app.touch_updated_at()`; `class_rules_touch_updated_at` → `app.enforce_class_rule()` (touches `updated_at`; refuses with `23514` any change to `service_id`, `branch_id`, `weekday`, `start_time`, `created_at`); `class_sessions_touch_updated_at` → `app.enforce_class_session()` (touches; refuses `23514` a change to `service_id`, `branch_id`, `rule_id`, `created_at`, or to `session_date` of a rule session; refuses `GL111` any change to a `cancelled` row other than `updated_at` and any `cancelled → scheduled` move); `class_bookings_touch_updated_at` → `app.enforce_class_booking()` (touches; refuses `23514` a change to `session_id`, `member_id`, `created_at`; refuses `GL113` any edge outside the table below; the edge `booked → session_cancelled` additionally requires the session row to be `cancelled`). These bind **every** writer, including the definer commands and `service_role`.

**Legal booking edges** (the only ones `app.enforce_class_booking` admits; gate 14): `booked → cancelled_by_member | cancelled_by_gym | session_cancelled | attended | no_show`; `cancelled_by_member → booked`; `cancelled_by_gym → booked`; `attended → booked | no_show`; `no_show → booked | attended`; `session_cancelled →` nothing. Same-status writes are legal. Who may take an edge is decided by the commands (CLS-012…CLS-018), not the trigger.

**Windows.** `p_from`/`p_to` are inclusive branch-local dates: null, `p_from > p_to`, or `p_to - p_from > 30` raises `22023` (CLASS_LIMITS.readWindowMaxDays = 31 days).

**`availability` values** (derived read-model label, not a stored vocabulary): `open`, `booked`, `full`, `closed`, `cancelled`, `membership_not_live`. First match wins: session `cancelled` → `cancelled`; the caller's booking row holds (`booked`/`attended`/`no_show`) → `booked`; `statement_timestamp() >= starts_at`, or the service inactive, or the caller's row is `cancelled_by_gym` → `closed`; no live membership on `session_date` → `membership_not_live`; `booked_count >= capacity` → `full`; else `open`. `can_cancel` is true iff the caller's row is `booked`, the session is `scheduled`, and `statement_timestamp() <= cancel_by`; `cancel_by = starts_at - class_cancel_window_hours * interval '1 hour'`, non-null iff the caller's row is `booked`. `spots_left = greatest(capacity - booked_count, 0)`; `booked_count` counts holding statuses. `trainer_name` is `staff.full_name` or null — never a staff id, phone or email.

**Which sessions `read_member_class_schedule` returns:** the caller's tenant (claim) and gym eligible; branch = the caller's home branch, or every branch when `class_allow_cross_branch`; `session_date` inside the window; and either (`session_status = 'scheduled'` and the service active) or the caller holds *any* booking row on it (so their cancelled and frozen-service bookings stay visible). No other member's identity, id or booking row appears in any column.

**Refusal order for every command** (the order is contract; the first failing step wins): (1) actor and role, `42501`; (2) null or malformed arguments, `22023`; (3) target unknown or in another gym, `42501`; (4) gym eligibility; (5) the command's state refusals in this order —

**Marking window** (`mark_class_attendance`): `attended` is accepted from `starts_at - 60 minutes`; `no_show` from `starts_at`; `booked` (undo) any time; all until `ends_at + 24 hours`; outside it `GL111`. Any target status other than these three raises `22023`. Allowed actors: owner, manager, front desk for any session; a trainer only for a session whose `trainer_staff_id` is theirs (otherwise `42501`).

**Limits** (mirrored in `CLASS_LIMITS`; SQL carries the same literals and a parity test pins them): horizon 28 local days; read window 31 days; name ≤ 80; description ≤ 500; duration 5–480 minutes; capacity 1–500; sort order 0–1000; cancel window 0–168 hours (default 2); marking lead 60 minutes and grace 24 hours; reason 3–200 trimmed characters; at most 50 services and 200 active rules per gym.

## EARS requirements

**Catalogue and timetable**

- **CLS-001 (create a service).** WHEN a real gym owner or manager (not impersonating) creates a service with a trimmed name of 1–80 characters unique in the gym case-insensitively (active or not), an optional description of at most 500, a default duration of 5–480 minutes, a default capacity of 1–500 and a sort order, THE SYSTEM SHALL insert one active `services` row (name stored trimmed, blank description stored null) and write `service.created`. A sort order outside 0–1000 SHALL raise `22023`; a taken name `23505`; the 51st service in a gym `GL114`; any other role (front desk, trainer, member, platform, impersonator) `42501`. A service is never deleted: disabling (CLS-003) is its only retirement.
- **CLS-002 (edit a service).** WHEN an owner or manager updates a service THE SYSTEM SHALL change exactly those five fields and write `service.updated` with only the changed keys; an update that changes nothing SHALL write nothing. Defaults are prefills only: editing them SHALL NOT change any existing rule or session (each is a snapshot).
- **CLS-003 (disable and enable — freeze and finish).** WHEN an owner or manager sets a service inactive THE SYSTEM SHALL (a) refuse new rules and sessions against it (`GL110`), (b) generate nothing for its rules, (c) refuse new bookings on its existing sessions (`GL092`), (d) leave every existing session and booking untouched — members may still cancel inside the window, the desk may still mark attendance — and (e) hide its sessions from members who hold no booking on them. Setting it active again SHALL immediately generate the missing sessions of its active rules (CLS-006). A call that does not change the state SHALL return false and write nothing; a change writes `service.deactivated` or `service.activated`. Disabling SHALL NOT cancel, notify or delete anything.
- **CLS-004 (weekly rules).** WHEN an owner or manager creates rules for an active service at a branch of the gym THE SYSTEM SHALL insert one `class_rules` row per distinct requested weekday in a single transaction (weekday 0–6; start time; duration 5–480; capacity 1–500; optional eligible trainer; `valid_from` defaulting to the branch-local today; optional inclusive `valid_until` not before `valid_from`), write one `class_rule.created` per row, run the generator for those rules (CLS-006) and return the sessions created per rule. A second active rule with the same branch, service, weekday and start time SHALL be refused `23505`; an empty, over-long, duplicated or out-of-range weekday list `22023`; more than 200 active rules in the gym `GL114`. An eligible trainer is an active staff row of the gym with role `trainer`, `gym_manager` or `gym_owner` that is unbound or bound to the rule's branch.
- **CLS-005 (edit a rule — propagation).** WHEN an owner or manager updates a rule's duration, capacity, trainer, `valid_until` or active flag THE SYSTEM SHALL update the rule (its service, branch, weekday and start time are immutable; changing them is "end this rule, create another") and apply the change to its **future** (`starts_at > now`), `scheduled`, never-individually-edited (`customised_at is null`) sessions as follows, taking the per-session booking lock in `(starts_at, id)` order after the rule row lock: capacity applies to all of them (bookings stand even if capacity falls below them; new bookings are refused until seats free); trainer applies to all of them and notifies their booked members (CLS-011); duration applies only to sessions with no holding booking; sessions past a new `valid_until`, or all future sessions when the rule is deactivated, are removed if and only if they have no booking row of any status (CLS-007's deletion rule) and are otherwise left as they are; finally the generator fills missing dates. THE SYSTEM SHALL return `sessions_created`, `sessions_updated`, `sessions_removed` and `sessions_kept` (sessions the edit wanted to change or remove but left because of bookings) and write `class_rule.updated` carrying them. Sessions with a `customised_at` SHALL never be touched by a rule edit.
- **CLS-006 (generation).** THE SYSTEM SHALL keep, for every active rule of an active service in an eligible gym, one session per matching local date from the branch-local today through today + 27, created idempotently on `(tenant, rule, session_date)` with `starts_at = app.class_local_instant(branch timezone, date, start_time)`, `ends_at = starts_at + duration`, the rule's capacity and trainer, and `session_date` the branch-local date of `starts_at`. Dates on `organization_holidays` SHALL be skipped. A session whose `starts_at` is not after `statement_timestamp()` SHALL NOT be created. The generator SHALL run inside CLS-004, CLS-005 and CLS-003 re-enable, and daily at 19:00 UTC through `public.run_class_generation_all()`; it SHALL be a no-op on re-run, SHALL never recreate an occurrence whose row exists (including a `cancelled` one — an owner-cancelled occurrence is never resurrected), and SHALL NOT raise on data conditions (an unknown timezone falls back through the gym's to UTC).
- **CLS-007 (holidays added later; the only deletions).** WHEN the generator runs and a rule-generated, never-customised, `scheduled` future session falls on an `organization_holidays` date THE SYSTEM SHALL delete it if and only if no `class_bookings` row of any status references it, writing `class_sessions.pruned` with the count; a session that has any booking row SHALL be left in place and surfaced by `read_class_timetable.on_holiday`. Removing a holiday SHALL let the next generator run recreate the skipped dates inside the horizon. These derived-row deletions (and CLS-005's) are the **only** deletions in the feature; they are performed by definer code taking the session's booking lock first, and the composite foreign key makes deleting a session that has a booking impossible.
- **CLS-008 (one-off sessions).** WHEN an owner or manager creates a one-off session (service active, branch of the gym, branch-local date from today through today + 27, start time, duration 5–480, capacity 1–500, optional eligible trainer, start strictly in the future) THE SYSTEM SHALL insert a `scheduled` `class_sessions` row with null `rule_id` and write `class_session.created`. A holiday SHALL NOT block an explicit one-off. A second scheduled one-off with the same branch, service and start SHALL be refused `23505`.
- **CLS-009 (edit one session).** WHEN an owner or manager edits an open session (`scheduled`, `ends_at > now`) THE SYSTEM SHALL under the booking lock: allow any capacity of 1–500 at any time (existing holding bookings stand, `spots_left` floors at 0, new bookings are refused `GL090` until a seat frees); allow trainer reassignment at any time (bookings stand; CLS-011 notice when the new trainer is non-null); allow a change of date, start time or duration only while no holding booking exists (`GL112` otherwise), and never a date change on a rule-generated session (`22023`; cancel it and create a one-off). A real change SHALL set `customised_at` (detaching the session from rule propagation; for a one-off session `session_date` follows a changed date) and write `class_session.updated` with the changed keys; an identical call writes nothing. A `cancelled` or ended session SHALL be refused `GL111`.
- **CLS-010 (cancel a session).** WHEN an owner or manager cancels a `scheduled` session whose `ends_at` is in the future with a reason of 3–200 trimmed characters THE SYSTEM SHALL, in one transaction holding the session's booking lock: set it `cancelled` with `cancelled_at`, `cancel_reason` and `cancelled_by_staff_id`; move every `booked` booking to `session_cancelled` with `cancelled_at` (never `no_show`, never `cancelled_by_*`), leaving `attended` and `no_show` rows as marked; write one notice per affected member (CLS-011); write `class_session.cancelled`; and return `bookings_cancelled`, `notices_written`, `notices_withheld`, `members_without_app` (members among the affected who have no linked app account, so the desk can phone them). Cancellation is irreversible, the occurrence is never regenerated, and a failure to write any notice SHALL roll the whole cancellation back. Already cancelled or ended: `GL111`. Front desk, trainer, member, platform and impersonator: `42501`.
- **CLS-011 (notices — shared primitive 3).** For each affected `booked` member of a cancelled session, and for each `booked` member of a session whose trainer was changed to a non-null trainer (CLS-005, CLS-009), THE SYSTEM SHALL write to `notifications` in the same transaction one row with channel `in_app`, category `class_update`, `template_key` `class_session_cancelled` or `class_trainer_changed`, `related_type` `class_session`, `related_id` the session, `scheduled_for` the command clock, `dedupe_key` `class-cancelled:<session_id>:<member_id>` or `class-trainer:<session_id>:<member_id>:<new_trainer_id>:<epoch microseconds of the command>`, and `payload` `{ body, kind, sessionId }` plus `reason` (cancel) or `trainerName` (trainer change); it SHALL then move the row `scheduled → sent` in the same transaction (the renewal-scheduler path), so the existing member inbox shows it with no new code. Bodies, with the session's service name and branch-local date and time: "{service} on {d Mon yyyy} at {h:mm am/pm} has been cancelled. Reason: {reason}" and "{service} on {d Mon yyyy} at {h:mm am/pm} will now be led by {trainer name}" (for example "Zumba on 12 Oct 2026 at 6:00 pm has been cancelled. Reason: Instructor unwell"). A notice SHALL be withheld (counted in `notices_withheld`, no row) only when the member is `cancelled`, `blocked` or erased, or their latest `service`-purpose consent row exists and is a withdrawal; an absent consent record does not withhold a transactional class notice. `class_update` is transactional: it needs no marketing consent. A duplicate dedupe key SHALL write nothing and count as written (the notice already exists). A member with no linked app account still gets the row (visible if they later link) and is counted in `members_without_app`.

**Booking**

- **CLS-012 (book — member).** WHEN a real member (cookie or bearer; never staff, never an impersonator; account not `cancelled`/`blocked`/erased) books a session of their own gym THE SYSTEM SHALL, taking `app.booking_lock(tenant, 'class_session', session)` as its first locking statement, apply in order: `GL092` if the gym is ineligible, the session is `cancelled`, `statement_timestamp() >= starts_at`, its service is inactive, or the member's own row is `cancelled_by_gym`; `GL094` if the member's home branch differs from the session's and `class_allow_cross_branch` is false; `GL091` if the member already holds a seat (`booked`, `attended`, `no_show`); `GL093` if the member has no live membership on `session_date` (CLS-013); `GL090` if the holding count is at or above capacity. Otherwise it SHALL insert the `booked` row (or revive one, CLS-015), write `class_booking.booked`, and return the booking id, status and `spots_left`. An unknown or other-gym session SHALL raise `42501`. The member's own tenant, member id and branch come from the verified claims and the member row, never from arguments.
- **CLS-013 (live membership).** THE SYSTEM SHALL treat a member as bookable only when `app.class_membership_live(tenant, member, session_date)` is true — a `memberships` row with status `active` or `frozen` whose `starts_on`/`ends_on` (null = open) include `session_date`, the branch-local day of the session (the branch timezone, falling back to the gym's, as check-in derives it). A parity test SHALL run the helper and the predicate in `app.enforce_check_in` over the same fixture matrix (active, frozen, pending, expired, cancelled; null and boundary dates) and require identical answers. A pending renewal does not make later sessions bookable.
- **CLS-014 (capacity and concurrency).** THE SYSTEM SHALL serialize every command that books, cancels, marks, changes capacity or time of, or cancels a session under that session's `app.booking_lock`, taken before any count or decision and re-counting inside the transaction. Two members booking the last seat concurrently SHALL produce exactly one `booked` row and one `GL090`; one member booking twice concurrently SHALL produce one row and one `GL091` (the unique key is the backstop). The holding count never exceeds capacity through booking, and a capacity reduction below the holding count SHALL leave existing bookings valid (CLS-009). Tests SHALL prove the lock both single-session (the transaction holds the advisory key afterwards) and with two real connections (gate 17).
- **CLS-015 (re-booking).** WHEN a member whose row is `cancelled_by_member` books the same session again (or the desk books a member whose row is `cancelled_by_member` or `cancelled_by_gym`) THE SYSTEM SHALL update that row to `booked` — new `booked_at`, `cancelled_at`/`cancel_reason` cleared, `acted_by_staff_id` set for the desk — rather than insert a second row, and audit it with `before.status` the previous status. A member whose row is `cancelled_by_gym` SHALL NOT be able to revive it themselves (`GL092`).
- **CLS-016 (member cancel and the window).** WHEN a member cancels their own `booked` booking and `statement_timestamp() <= starts_at - class_cancel_window_hours hours` (inclusive; a window of 0 allows cancelling until the start) THE SYSTEM SHALL under the booking lock set `cancelled_by_member` with `cancelled_at` (clearing `acted_by_staff_id`), freeing the seat, and write `class_booking.cancelled`. Inside the window the booking SHALL stay `booked` and the call SHALL raise `GL095`; after the session has started that is also `GL095`. A row that is not `booked` (already cancelled, attended, no-show, session-cancelled) SHALL raise `GL113` first. Another member's booking, an unknown id and another gym's id SHALL be indistinguishable `42501`. The window read is the gym's *current* setting at the time of the call; a missing settings row means the default 2.
- **CLS-017 (desk booking and cancelling).** WHEN a real owner, manager or front-desk user books a member of their gym into an open session (`ends_at > now`, so a walk-in may join a class in progress) THE SYSTEM SHALL apply CLS-012's order and checks to that member (a `cancelled`, `blocked` or erased member is `GL093`), set `acted_by_staff_id`, and write `class_booking.booked` with `via: 'desk'`. WHEN they cancel a `booked` booking with a reason of 3–200 trimmed characters before `ends_at` THE SYSTEM SHALL set `cancelled_by_gym`, record the reason and actor, and write `class_booking.cancelled_by_gym`; there is no window for the gym. Neither command overrides capacity, membership or branch rules, and a trainer is refused `42501`.
- **CLS-018 (marking attendance).** WHEN an owner, manager or front-desk user — or a trainer for a session they lead — marks a booking `attended`, `no_show`, or `booked` (undo) THE SYSTEM SHALL, under the booking lock, apply it only from `booked`, `attended` or `no_show` and only inside the marking window (`attended` from 60 minutes before the start, `no_show` from the start, both until 24 hours after the end; the session must not be cancelled), set or clear `marked_at` and `acted_by_staff_id`, and write `class_booking.attendance_marked`. A repeat of the current status SHALL write nothing and return the status. The sole sources of `attended` and `no_show` are these calls.
- **CLS-019 (a booking is not attendance).** THE SYSTEM SHALL NOT insert or change any `attendance` row, `no_show_cases` row, follow-up or streak input because of a booking, a cancellation or a mark, and no trigger on those tables is added or altered; a booked member who does not check in is exactly as visible to the no-show scan as one who never booked. Nothing converts an unmarked booking of an ended session into `no_show`; the read models label such a row "Not marked". Tests SHALL assert the row counts and contents of `attendance` and `no_show_cases` are unchanged by every command.
- **CLS-020 (state machine).** `app.enforce_class_booking` SHALL admit only the legal edges in "Fixed names" for every writer, raising `GL113` otherwise (the illegal-transition tests of gate 14 cover all 36 ordered pairs, the same-status writes, and the `session_cancelled`-requires-a-cancelled-session rule), and SHALL keep `session_id`, `member_id` and `created_at` immutable (`23514`).

**Reads, security, time, audit**

The cross-tenant leak suite of gate 7 SHALL cover all four tables for every role.
- **CLS-022 (member read surface).** THE SYSTEM SHALL let a real member read classes only through `public.read_member_class_schedule`, which derives tenant, member and branch from the claims, applies the visibility rule in "Fixed names", and returns counts only: `booked_count` and `spots_left`, the member's own booking id and status, the trainer's display name and nothing about any other member. It SHALL raise `42501` to any caller that is not a complete real member, and `22023` on a bad window. Tests SHALL grep every returned column set and every row for the other members' names, ids and phones.

- **CLS-026 (time).** THE SYSTEM SHALL decide every "now" with `statement_timestamp()`; derive every local day and wall-clock instant through `app.class_branch_timezone` and `app.class_local_instant` (MNY-004/005); store `session_date` as the branch-local date of `starts_at`; treat a session that crosses local midnight as belonging to its start date; and resolve a nonexistent or ambiguous local time by PostgreSQL's `AT TIME ZONE` rule, which a test SHALL pin for one spring-forward and one fall-back date in a DST zone. A session cancel writes no per-booking audit rows (the counts and the notification triggers' own rows cover them). Refusals write nothing.

## ADR-183 text

**ADR-183 — Services, classes and booking: materialized sessions, freeze-and-finish, and a booking that is never attendance (owner-approved feature map F2, 2026-10-02).** Decisions, each with the alternative rejected. (1) *Rules plus concrete rows.* A weekly rule generates dated `class_sessions` over a 28-day rolling horizon; bookings reference a row. Rejected: occurrences computed on read with a `(rule, date)` booking key — every read would recompute holidays and edits, no foreign key could protect a booking, and a cancelled occurrence needs a row anyway. (2) *Generation is idempotent and everywhere.* Every rule command generates immediately and a daily job tops up; the key `(tenant, rule, session_date)` makes re-runs free and means an owner-cancelled occurrence is never resurrected. Rejected: generate-on-read (a write on a GET) and unbounded horizons. (3) *A rule's identity is immutable.* Weekday, local start, service and branch never change; "move the class" is end-and-create, the calendar vocabulary of "this and following". Rejected: reconciling old and new occurrences by date, which has no honest mapping when the weekday moves and silently rewrites what booked members agreed to. Capacity, trainer, duration, end date and active flag propagate to future, never-individually-edited sessions; duration only where nobody holds a seat. (4) *The system never cancels a session that has bookings.* A disabled service, an ended rule, a holiday added later and a deactivated trainer all leave booked sessions standing; only an explicit owner or manager action cancels, and that action notifies. Disabling a service therefore means freeze-and-finish: nothing new may be scheduled or booked, everything promised is honoured. Rejected: cancel-with-notice on disable — one misclick would cancel and message every booked member, and a toggle is not a decision to cancel. Bulk "cancel all upcoming" is a possible later convenience, not a side effect. (5) *Only derived, never-booked rows are ever deleted,* by definer code that takes the session's booking lock first, with the composite foreign key as the backstop; everything else is cancelled, never removed. (6) *One booking row per member per session.* Cancel then re-book revives the row; history is the audit log. Rejected: a row per attempt (unbounded churn from a cancel/book loop and a partial-unique rule to explain). Capacity counts `booked`, `attended` and `no_show` — a no-show does not free a seat, because the class has begun. (7) *A booking is not attendance, and nothing infers it.* `attended` and `no_show` come only from explicit desk or assigned-trainer marking, audited, inside a window. Rejected: a trigger on `attendance` that flips bookings (a silent coupling inside the check-in trigger this product is sold on) and a sweeper that turns unmarked bookings into no-shows (it would assert an absence nobody observed; an unmarked past booking reads "Not marked"). ATT, NSH and STK are untouched. (8) *Members read through definer RPCs; there is no member policy on the tables.* The branch filter, the disabled-service filter, the trainer's name without a staff id, and counts-only capacity are not expressible as row policies, and the INV precedent is a table members cannot read. Staff roster visibility is the whole staff gate (`is_staff`): the matrix has four gates and no fifth, and staff already read `members` and `attendance` gym-wide. (9) *Membership test mirrors check-in.* `active` or `frozen`, inclusive dates, null open, judged on the session's branch-local day (branch timezone, then the gym's), as a helper with a parity test against `app.enforce_check_in`; the trigger itself is not refactored in this change. Whether a frozen member should be bookable is a product question recorded for the owner; parity is the safe default. (10) *Cross-branch booking is refused by default* with a per-gym switch, matching the poster refusal. (11) *Notices ride the existing rails.* `class_update` is a new `message_category` value; the notice is a `scheduled` then `sent` in-app `notifications` row written in the cancelling transaction, exactly as the renewal scheduler does, deduped per session and member, withheld only for an ineligible member or an explicit service-consent withdrawal (an absent consent record is not a withdrawal), and counted back to the cancelling staff, including members with no app. Because PostgreSQL forbids using an enum value added in the same transaction, every assertion that touches the label lives in its own pgTAP file that can pass only in CI. (12) *CLS-only refusals take a new block `GL110…GL114`;* `GL090…GL096` are the shared booking vocabulary and `GL097…GL099` stay reserved for it. Trainer overlap is advisory (`GL096` belongs to PT slots): studios legitimately run an assistant alongside a lead. (13) *The cancel window is per gym, in whole hours, 0 to 168, evaluated at call time, inclusive at the boundary.* (14) *Settings are plain `organization_settings` columns:* a guard trigger would add a second substantive trigger to a table the meta-suite pins, and the table's other settings are equally unaudited. (15) *Reschedule of a booked session is refused* (`GL112`): changing a start time under booked members is a cancel-and-recreate, because the cancel window and the members' plans were made against the old time.
