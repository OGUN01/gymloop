## Approved decision and its source

The owner approved one narrow exception to `docs/architecture.md` line 46: “Supabase Edge Functions are used for exactly two things … Nothing else runs as an Edge Function”. Add a dedicated trusted verifier `supabase/functions/media/index.ts`, reachable with a real caller JWT; operation is exactly `confirm`, `member-url` or `staff-url`. Requests contain exactly `{ operation, assetId }` with a UUID id (no actor, tenant, key or metadata fields); invalid/extra fields are 400 invalid_request after caller identification. The runtime's existing `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` serve its caller/service clients. No new database secret, cryptographic receipt or web-admin client is introduced. No assumption that an R2 credential is already provisioned to Edge, or that earlier CORS approval authorises this deployment.

The owner approved the concrete contract below, not a general permission for user-facing service-role access. ## Fixed names and storage model

- Web `POST /api/media/confirm` keeps `{ assetId }` and `{ assetId, confirmed: true }`. After verified session-first parsing it forwards the original bearer access token to `POST /functions/v1/media` with `{ operation: 'confirm', assetId }`; cookie sessions forward their verified session token. No token in JSON, log, URL or response. The Edge endpoint independently validates Auth token authenticity/expiry and complete real staff claims, and rechecks the active matching staff row and allowed kind via the caller's RLS client. Impersonation, platform, member, trainer, missing/contradictory claims and kind-forbidden front desk are refused before R2 access. Verification never trusts forwarded actor headers/body fields.
- `media_assets` adds `staging_object_key text not null`, `verified_source_etag text`, `published_etag text`. `object_key text` becomes nullable until confirmed. Both staging and published keys are tenant-unique separately; published `object_key` keeps `media_assets_tenant_id_object_key_key`. `media_assets_tenant_id_id_key` remains. Stored staging key = `<tenant_id>/staging/<kind>/<uuid>.<ext>`; published key = `<tenant_id>/published/<kind>/<fresh_uuid>.<ext>`. Stage/kind/tenant/MIME-extension checks bind each namespace. `confirmed_at`, `object_key`, both ETags are all null or all non-null; attached implies confirmed; deleted implies detached. The application never changes a finalized published key or creates a presigned PUT for a published key. Runtime trusted credentials retain write power; this is an application invariant, not a claim that R2 object locks are available.
- `register_media_asset(p_kind,p_object_key,p_mime,p_bytes)` retains its signature; `p_object_key` means a staging key exclusively. It sets `staging_object_key`, leaves published fields null, and cannot accept `/published/`. `buildMediaObjectKey` takes the additional fixed field `storageArea: 'staging' | 'published'`; parser returns it. Browser receives staging PUT only. Authenticated `media_assets` SELECT grants enumerate safe id/tenant/kind/MIME/bytes/creator/timestamp/attachment columns; staging/published keys and ETags are not granted to authenticated, and `select *` is never used. Credential-trusted service role may read the full row. Web upload creates its staging key itself; that upload URL still necessarily contains it. All `createMediaStorage.presignPut` call sites reject `/published/`, independently of callers; signing GET uses published only.
- Retained old `public.confirm_media_asset(p_asset_id uuid)` is a refused compatibility entrypoint (`42501`), with execution revoked from PUBLIC/anon/authenticated/service_role. It can never stamp confirmation. New `public.finalize_media_asset(p_asset_id uuid, p_actor_user_id uuid, p_actor_staff_id uuid, p_actor_role public.app_role, p_tenant_id uuid, p_kind text, p_mime text, p_bytes integer, p_staging_object_key text, p_source_etag text, p_published_object_key text, p_published_etag text) returns boolean` is SECURITY DEFINER, VOLATILE, empty path, owned by postgres, executable only by `service_role` (PUBLIC/anon/authenticated revoked). Before any write it checks the original connection role setting (`current_setting('role', true) = 'service_role'`) and signed request JWT role are both credential-only service-role, with no user subject/impersonation claims; actor claims are arguments accepted solely from the trusted verifier. Under active staff then asset row locks, it compares every supplied stored asset field, revalidates actor user/staff/tenant/role and kind permissions, rejects deleted or inconsistent assets, validates both namespaced keys and nonempty ETags, then stamps once. `true` means it finalized; `false` means this eligible asset was already confirmed, with no write/audit. Replay compares the immutable registration and active actor, but does not require the losing candidate key/ETags to equal the winning published tuple; this permits concurrent-attempt false without rewriting publication. Malformed verified metadata -> 22023; actor/tenant/role mismatch -> 42501; deleted asset -> GL086 media_not_ready. No general service-role table write or finalization-shaped authenticated grant is introduced.
- Invariant `media_assets_verified_immutable` (ROW BEFORE INSERT OR UPDATE OR DELETE) / invoker `app.enforce_media_asset_verification()` rejects inserting confirmed fields, changing staging/tenant/kind/MIME/bytes/creator identity, or changing published fields after confirmation. Finalization sets transaction-local `app.media_finalize_command = 'finalize:' || p_asset_id::text` only around the guarded update, restores the previous value immediately on return/exception, and the invariant admits only this exact marker plus credential-only connection/request service-role and postgres definer context (a marker alone never authorises authenticated callers). Only that exact finalization transition, changing null published fields to validated values plus confirmed_at, is admitted. Existing audited attachment/release/deletion commands may change only their named fields; these invariants bind postgres writers too. Physical media-row DELETE is refused in v2 with GL086 media_verification_invariant, even for trusted writers; a later retention contract may admit unreferenced rows only after canonical retention. INSERT must have null published/verification fields; all identity, registration and created_at fields stay frozen. The marker value is exactly `finalize:<lowercase canonical asset UUID>`; all other values fail the invariant. The finalizer calls private `app.media_audit` with verified actor arguments, so confirmation audit records the real staff actor even though service JWT has no user subject. No key, ETag or secret in audit. `app.enforce_media_asset_verification()` is invoker, VOLATILE, empty path, owned by postgres, execution revoked from PUBLIC/anon/authenticated/service_role; every refused identity/publication/DELETE shape raises GL086 with DETAIL media_verification_invariant (HTTP 500 media_failed).

## Verification, races, replay and failure

1. Caller-scoped safe asset lookup, active allowed actor validation, then Edge-only privileged lookup of staging/verification fields; an already-confirmed undeleted allowed asset returns success after active-actor validation with no new copy or audit. It never returns success for deleted/invisible/ineligible assets.
2. HEAD staging, record source ETag, exact registered size and MIME; ranged GET with `If-Match` that ETag, verify format magic bytes. Missing -> upload_missing; invalid size/MIME/signature -> upload_rejected and request caller `delete_media_asset(assetId, true)` (object cleanup best effort). That command locks the asset and is a no-op if a concurrent verifier has already confirmed it, so a rejected attempt never deletes another attempt’s published winner; source conditional failure -> upload_changed (409, “The photo changed while it was being checked. Choose it again and retry.”), with no confirmation.
3. Generate a fresh unpublished destination UUID per verification attempt; HEAD must find no existing destination, otherwise choose another. Copy with `CopySourceIfMatch` of the verified ETag, preserving/checking registered Content-Type. No multipart upload (2 MiB cap). Source replacement after ranged check makes this conditional copy fail. A subsequent replacement of the staging object cannot modify the independent published copy. Record copy result destination ETag, HEAD and ranged GET the published object against that ETag and independently recheck size, MIME and magic bytes. Any missing ETag, embedded copy error, unexpected metadata or failed post-copy verification fails closed; no finalization.
4. Call finalizer with independently verified actor tuple and exact stored metadata plus source/destination ETags. Active staff revocation, deleted asset or altered stored registration before finalization causes refusal. Concurrent verifiers each create different candidates; locked finalizer admits one. Loser observes false, removes only its own unreferenced candidate, and reports success only after rechecking the winner's confirmed/undeleted eligible state. Never remove another attempt's candidate or the winning published object.
5. Finalizer timeout is an unknown outcome: revalidate caller through its safe RLS projection first, then Edge-only privileged reread for candidate-key comparison. If candidate key is the confirmed winning key, keep it and return success. If a definitive completed finalizer outcome and authoritative reread prove another candidate won or the row was deleted, clean only this positively unreferenced candidate. An unconfirmed reread alone cannot prove an in-flight finalizer will not commit: retain the candidate, return retryable storage_unavailable and reconcile via the same locked finalizer request or later orphan procedure before deletion. Failed/ambiguous reread means no deletion of candidate; return retryable storage_unavailable and retain an orphan for later object-only cleanup. Never interpret timeout as rollback. Successful replay emits no duplicate confirmation audit.
6. Staging cleanup is best effort after successful confirmation. Reusing a still-live staging PUT may recreate or alter only staging; confirmation replays never recopy it. Later object-only orphan pruning may remove residual staging after upload URL expiry plus the 7-day threshold. No cleanup job is built in this feature.

[Cloudflare S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/) fetched 2026-10-02 documents conditional source matching for CopyObject and conditional/ranged GetObject. This supports the race design; it is not evidence that the deployed function or bucket passed verification. Live bucket conditional-copy behaviour must be demonstrated after approved deployment, before accepting upload UX.

## The member read boundary and history retention

Public caller-authenticated feature RPCs return only `image_asset_id` (null unless the current image is exposed), never object key/MIME/ETag. SHP `read_member_shop` / `read_member_shop_reservations`, PTF's trainer read and ANC `read_member_announcements` use that shape. Direct member PostgREST calls therefore reveal only an opaque asset id. Web/mobile read envelopes contain `imageUrl` only; no public “server projection” RPC under member JWT may recover keys. A signed URL necessarily contains an object path and temporary capability, so no promise that an authorised member cannot observe the image URL's key is made.

`memberMediaUrl(supabase, assetId)` forwards the original verified caller JWT and `{ operation: 'member-url', assetId }` to the same Edge `media` function; neither a web service client nor a client-supplied key is used. `POST /api/member/media-url` uses this adapter. Edge validates complete real member identity and binding, then reads current exposure through the **caller JWT** feature RPC: product in `read_member_shop`, trainer in the PTF member trainer read, announcement in `read_member_announcements` (including latest promotion consent and live/version rules). It finds the requested image_asset_id in that current response and retains its exposed item_id, trainer_key or announcement_id plus kind. Only after this exposure succeeds does its service client fetch private media metadata. For product and announcement assets, attached_to_id SHALL equal the exposed actual item_id / announcement_id. For trainer assets, attached_to_id is the actual private staff UUID, whereas exposed trainer_key is a pseudonym: derive app.pt_trainer_key(verifiedTenant, attached_to_id) by the exact canonical algorithm below and require it equals the returned trainer_key for the same image_asset_id; NEVER compare attached_to_id directly with trainer_key. It also checks verified tenant, correct kind, confirmed/undeleted state and published namespace before signing. Actual staff UUID stays private. It repeats caller exposure immediately before minting if any await separated exposure and privileged asset resolution; authorization withdrawal during a completed request remains bounded by response/URL issuance, not an instant-revocation promise. A cached feed, internal adapter omission or client-supplied parent never grants access.

### Trainer attachment pseudonym parity (fixed)

For a trainer asset only, use private attached_to_id after successful caller-JWT trainer exposure. Normalize verified tenant and private staff UUID through canonical UUID parsing to lowercase dashed text. UTF-8 input is exactly `pt-trainer:<tenant_uuid>:<staff_uuid>`, no whitespace, newline or braces. MD5 yields 32 lowercase hex characters; format as UUID groups 8-4-4-4-12, preserving every digest nibble. Do not impose UUID version/variant bits or use UUIDv3/v5. This is byte-identical to existing `app.pt_trainer_key(uuid,uuid) = md5('pt-trainer:' || tenant::text || ':' || staff::text)::uuid`. Require derived UUID equals caller-exposed trainer_key **and** the exposed image_asset_id equals the requested asset; no actual staff id is returned or accepted from the member.

Edge may use built-in `node:crypto` `createHash('md5').update(input,'utf8').digest('hex')`, confined to this Edge runtime (never packages/shared); no npm/Deno package, new public RPC or secret. [Official Deno Node crypto documentation](https://docs.deno.com/api/node/crypto/) fetched 2026-10-02 documents built-in import and createHash. Runtime MD5 capability and cross-runtime parity are mandatory verification, not assumed deployed evidence: if unavailable or divergent, signer fails closed storage_unavailable; never fall back to direct staff-id comparison or another hash.

Fixed independent parity vectors (not production identities): tenant `73000000-0000-4000-8000-000000000001`, staff `73000000-0000-4000-8000-000000000002` → trainer key `b0f1360f-0686-5c81-8076-6bb80756495d`; same tenant, staff `73000000-0000-4000-8000-000000000003` → `4da186b4-1472-ad0c-0fd5-2f778769be1d`. Test authors compare PostgreSQL helper and Edge builtin output to both vectors, plus uppercase UUID input normalization, foreign tenant/staff, mismatched pseudonym/image pair and no leaked actual staff id. These vectors were computed independently; no Cloud or Edge runtime acceptance test has been run in this contract session.

`mediaDisplayUrl(supabase, assetId)` uses `{ operation: 'staff-url', assetId }` on the same Edge function: caller-RLS safe asset read plus active allowed staff validation (support-preview reads only where existing SHP read policy permits), then privileged published-key read and same immutable verified-state checks. Confirm remains real-staff-only; preview may never finalize. GET TTL is `MEDIA_LIMITS.displayUrlTtlSeconds`. No end-user execute grant on any privileged key projection. Unauthorized/id-not-exposed → indistinguishable asset_not_found. Missing verified state → asset_not_found; infrastructure failure → storage_unavailable. No key/token/URL logging. All responses no-store.

Revocation prevents newly authorised URLs; already issued URLs may work for their remaining <=900s TTL. Stored keys grant no R2 access by themselves. Web `createMediaStorage` only presigns staging PUT; GET signing and verification are in the approved Edge boundary, approved.

MED-012 pruning becomes **objects only**: unconfirmed staging/orphan published objects after 7 days; released/deleted objects after 30 days. Retain `media_assets` metadata tombstones for the owning gym's canonical configuration retention (account closure + 8 years), and at least as long as any immutable announcement version references them; whichever is later. No physical metadata deletion while referenced, no cascade, SET NULL or history edit. ANC images that were replaced stay referenced in historic immutable versions but their released object may be absent; historical preview renders the existing placeholder. Tenant/id FK integrity remains true after object pruning. No personal data or original picture retained merely to keep the FK.
