# Design — 0001-data-model

Seven migrations, six of them written in parallel by agents that never see each other's files. The thing that makes that faster than writing them serially is a contract fixed before any of them starts; without one, parallelism buys six dialects and a reconciliation pass that costs more than it saved.

The contract itself is `docs/data-model.md` § **Conventions (the contract)** — naming, the table skeleton, the `app` schema and its two JWT accessors, the RLS template, the privilege tiers, the index rule, enum ownership, the audit-row shape, and the list of things a cluster agent must not do. It is not repeated here (`AGENTS.md` rule 1: one source, not two). This document records *why* it says what it says, what was rejected, and how the seven migrations reach `main`.

## Decisions

Four of them are already numbered ADRs and are not re-argued here: **ADR-031** (`app_role` is the one role vocabulary), **ADR-032** (the claim names, and the two `stable` `security invoker` accessors in a private `app` schema, with `NULL` on a missing claim and a loud cast failure on a malformed one), **ADR-033** (the two tenant-path exemptions are a closed list), **ADR-035** (uuid v4 primary keys, and why the departure from Supabase's identity-bigint guidance is deliberate). What follows is the rest of the contract, which has no ADR yet and probably wants one for the privilege model in particular — the `pg_default_acl` finding is the sharpest thing in this change and currently lives only in a docs section.

**`set search_path = ''` on all three `app` functions, including the trigger function.** ADR-032 covers the accessors' security context; the same reasoning extends to `app.touch_updated_at()`, which is `plpgsql` and therefore the more usual host for a search-path hijack. Fully-qualified references throughout, so an empty search path costs nothing.

**Two permissive policies, not one predicate.** `tenant_id = claim OR is_platform()` in a single policy would work and reads shorter. Two named policies win because `docs/security.md` requires the platform branch to be *a separate policy branch keyed on role* that can be inspected, tested and later revoked on its own, and because a pgTAP test can assert the presence and shape of `<table>_platform_all` by name. Permissive (OR), not restrictive (AND): a restrictive pair would require both conditions and lock everyone out.

**`(select app.current_tenant_id())`, not `app.current_tenant_id()`.** Wrapping a `stable` function call in a scalar subquery lets the planner hoist it into an InitPlan evaluated once per statement instead of once per row. It is Supabase's documented RLS performance rule, and the difference shows up on exactly the tables that matter — `attendance`, `notifications`, `payments`. It is in the contract as a template rather than as advice because six agents copying a template get it right and six agents remembering a rule do not.

**Per-table `revoke`/`grant`, not `alter default privileges`.** Verified against `pg_default_acl`: in `public`, every table created by `postgres` is granted ALL to `anon` and `authenticated`, including `delete` and `truncate` — and `truncate` is not filtered by RLS at all. So RLS alone is not a security boundary here; the privilege has to be taken away explicitly. `alter default privileges in schema public revoke all on tables from anon, authenticated` in the contract migration would fix it once and was rejected as *the* mechanism: it silently changes the behaviour of every future object created by any tool including Studio, it is invisible at the point where a reader is auditing a table, and it does not apply to objects created by a different role. The per-table lines are greppable and are what the pgTAP privilege meta-test asserts. A later ADR may add the default-privileges line as a second belt; it may not replace the first.

**No `force row level security`.** `force` exists to subject the table owner to its own policies. The owner is `postgres` — the role that applies migrations and runs the seed, holding no JWT — so under `force` every policy evaluates against a null claim and the seed writes nothing. The role that carries a user request is `authenticated`, and that is the role the cross-tenant suite proves isolation for (gate 7). Written into the contract explicitly so a future reader does not "fix" the omission.

**`delete` is granted to no role on no table in Phase 1.** INT-001 forbids hard-deleting financial records, attendance corrections and follow-up history; no v1 flow deletes anything else either. Withholding the grant everywhere is one rule instead of a per-table judgement, and it makes the pgTAP assertion trivial ("`authenticated` holds `delete` on nothing"). The `history` and `normal` tiers therefore emit the same grant today and are still named apart, because on a history table the absence is permanent and on a normal table it is a default a later phase may deliberately lift.

**Append-only is a privilege, not a trigger.** `consents`, `follow_ups`, `attendance_corrections`, `audit_log`, `messaging_wallet_ledger` and `webhook_events` get `select, insert` and nothing more. A `before update ... raise exception` trigger would express the same rule and was rejected: it is behaviour in the database, which Phase 1 does not own, and it can be dropped by anyone who can drop a trigger. A missing grant cannot be forgotten by a code path.

**One cluster owns each enum, listed as a table in the contract.** Two agents both writing `create type public.app_role` is not a merge conflict — the files do not overlap — it is an apply failure discovered on `main` after CI has already run the first one. Ownership is derived from which cluster's tables first need the type; `app_role` is pulled forward into the contract migration because four clusters use it.

**pgTAP into `extensions`, and only two extensions in Phase 1.** `extra_search_path` in `config.toml` already covers `extensions`, so test files need no qualification. `btree_gist` belongs to the catalogue cluster because `pt_sessions`' double-booking exclusion is its only user. `citext` (available, not installed) was considered for `gym_code` and `email` and rejected: two columns do not justify a type dependency that shows up in generated types, and both are normalised at the application boundary anyway.

## Cluster and merge plan

| Merge | Cluster | Creates | Blocked by |
|---|---|---|---|
| 1 | **tenancy** (the contract migration) | `pgtap`, schema `app` + the three functions, 5 enums, `organizations`, `organization_settings`, `branches`, `staff`, `members` | — |
| 2 | membership+money | 6 enums, 11 tables | tenancy (`organizations`, `members`, `staff`) |
| 3 | attendance | 1 enum, 4 tables | membership+money (`memberships`) |
| 4 | catalogue | `btree_gist`, 3 enums, 3 tables | membership+money (`payments`) |
| — | retention · comms · platform | 3 enums + 2 tables · 3 enums + 6 tables · 3 enums + 5 tables | tenancy only — any order, any time after merge 1 |

Merge 1 lands alone and is verified green on `main` before the other six start: they all reference `organizations`, call `app.current_tenant_id()`, and use `app_role`, so a fan-out that begins before it exists is six agents guessing at the same objects. A cluster never references a table from a cluster that merges later; where two clusters share a seam the later table carries the foreign key (`addon_orders.payment_id`), never an `alter table` against the earlier one. `db.yml`'s `concurrency` group serialises the applies, so merge order is whatever order the PRs are merged in — the numbering above is the constraint, not a schedule.

Each cluster is **two commits in one push to `main`** (`AGENTS.md` rule 10 and the owner's trunk-only decision of 2026-09-06, commit `964cf99`): the pgTAP file first, then the migration that turns it green. This design originally described two pushes to a pull request, and that is no longer the workflow — there are no branches and no PRs, so the shape of the evidence changes with it.

`check-test-immutability` is a **per-commit** gate, not a per-push one, so two commits in a single push satisfy rule 10 exactly as two pushes would: the history still shows the test authored before the DDL that answers it. What one push gives up is the red CI run in between. On `main`, `db.yml` skips nothing — the PR-only skip in `pgtap`/`schema-drift` does not apply — so a tests-only push would apply no migration and run the suite against tables that do not exist, leaving `main` red until the next push. That is a deliberately broken trunk, on a repo whose rule is that `main` stays green.

**So the red run is bought once, not seven times.** The `tenancy` contract cluster pushes its tests alone first and the red `db.yml` run is recorded as evidence that the pgTAP runner discriminates rather than passing vacuously — the "a red job is not evidence until you read why" lesson from Phase 0, applied to the one gate Phase 1 introduces. The six fan-out clusters then push tests and migration together, keeping `main` green. Recorded as an open decision for the owner.

**Generated types cannot be regenerated by a cluster agent.** `supabase gen types` reads Cloud, and Cloud has nothing until `migrate` runs on the push. So cluster commits never touch `packages/db/types/database.ts`; the orchestrator pushes one regeneration commit to `main` immediately after each apply, and a cluster is not done until that commit is green. `schema-drift` is red on `main` for the window between the apply and the regeneration commit, which is the honest cost of a schema landing through CI and should stay visible. The alternative — `migrate` committing the regenerated file itself — makes CI a committer of source, and is an orchestrator decision that has not been taken.

## Out of scope, and named so nobody builds it early

The custom access-token hook that actually sets `tenant_id` and `app_role` (Phase 2 — Phase 1 fixes the claim names and the accessors that read them, nothing more) · any per-role policy beyond tenant isolation, and any third accessor (Phase 2's role matrix) · every audit write, including triggers (Phase 3+, INT-003) · state-machine enforcement and illegal-transition tests, which arrive with the phase that first mutates each status (3, 4, 5; gate 14) · the money rounding rule (Phase 5, MNY-003) · Vault wiring for the Razorpay secret ids (Phase 5) · `pg_cron` jobs of any kind (Phase 4, and OPEN-007 first).

## Owed by this change, not yet done

`docs/registry.md` has no entry for `app.current_tenant_id()`, `app.is_platform()`, `app.touch_updated_at()` or any of the 24 enums — hard rule 1 makes that a `registry-lint` concern the archive step has to close, and the enums are the half that matters, since they become the generated TypeScript unions everything downstream imports. The privilege contract (per-table `revoke`, three tiers, no `delete` anywhere, nothing for `anon`) and the no-`force` rule have no ADR number; they are decided and written into `docs/data-model.md`, but a reader looking for *why* currently finds only this file.
