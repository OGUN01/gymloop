# Android Data safety — Play Console answer sheet

**Scope:** Current Android source in `apps/mobile` and its `@gymloop/api-client` dependency, checked 24 September 2026. This is an answer sheet, not a submission. Play defines **collected** as data transmitted from the app off the user's device; simply receiving data from our server and displaying it is not an outbound collection. Data processed ephemerally must still be answered in the form even if it is not displayed in the public section ([Google Play Data safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469)). A field stored on our server because the **web app or gym** entered it is not automatically collected *by this Android app*. Recheck the exact AAB before submitting: the recorded 1.0.0 production bundle predates some current source changes (`docs/evidence/2026-09-20-phase8-production-release.md:69-75`).

## High-level Console answers

- **Does this app collect user data?** Yes: sign-in credentials/identifiers, check-in actions, optional walk-in leads, desk-assisted check-ins and follow-up actions. Each affirmative data-type row below gives the outbound source line.
- **Does this app share user data?** No identified sharing outside providers acting on our behalf for the audited app flows. Supabase hosts Auth and database; Vercel hosts the first-party API; Cloudflare R2 holds service backups (`apps/mobile/lib/mobile-context.tsx:35-43`; `apps/web/app/(public)/privacy/page.tsx:36-40`). Google sign-in is an **optional, user-initiated third-party OAuth flow**; see UNCERTAIN note before marking the sharing answer final. Do not call Google a storage service provider for this flow.
- **Encrypted in transit?** Yes for the **inspected 1.0.0 production bundle**: its compiled Android JS contains `https://gymloop-phi.vercel.app` and `https://pecxrpskmfeuyzngvewq.supabase.co` (inspected `dist/releases/gymloop-1.0.0-2-production.aab`, `base/assets/index.android.bundle`). Code passes the public URLs to Supabase and the API client, whose POST carries the bearer token (`apps/mobile/lib/mobile-context.tsx:34-43`; `packages/api-client/src/index.ts:26-37`). The recorded production API origin is HTTPS (`docs/evidence/2026-09-20-phase8-production-release.md:61-68`). **UNCERTAIN for future builds:** the mobile env schema accepts any `z.url()`, including HTTP; it does not enforce HTTPS (`packages/shared/src/config/env.ts:19-23,91-97`). Confirm both endpoints in the *actual uploaded* AAB and OAuth redirect before answering again.
- **Can users request data deletion?** Yes, **by request, not instant self-service**: member You and staff More link to the public `/delete-account` page (`apps/mobile/components/legal-links.tsx:7-26`; `apps/mobile/app/(member)/you.tsx:34-36`; `apps/mobile/app/(desk)/more.tsx:55-57`). The page asks users to email support from the sign-in address or ask their gym, and describes review and retained financial/consent records (`apps/web/app/(public)/delete-account/page.tsx:11-30`). Submit `https://gymloop-phi.vercel.app/delete-account` as the external deletion-request URL. **Release blocker:** `SUPPORT_EMAIL` is currently a `.example.com` placeholder (`packages/shared/src/config/constants.ts:21-22`); replace it with a working inbox and verify the live pages/new AAB before asserting requests can actually be received.
- **Advertising, analytics and crash-reporting SDKs:** None declared in `apps/mobile/package.json:12-39`, and no calls to those SDKs in the audited `apps/mobile/app/` or `apps/mobile/lib/` code. `expo-updates` **is** listed (`apps/mobile/package.json:29`); it is not an analytics SDK, but inspect the final native bundle/network behavior for any independently transmitted installation ID before answering Device or other IDs definitively.

Except where explicitly flagged, data written to Auth, the database or the API is **not processed ephemerally** because an account, attendance, lead or action history persists. The API attaches a bearer token to each POST (`packages/api-client/src/index.ts:27-34`); Supabase reads and writes use the signed-in client (`apps/mobile/lib/native-session.ts:81-88`). The mere transmission of a downloaded member record *to* the device is not collection *from* the device, although query selectors, auth tokens and any write payloads sent back off the device are in scope.

## Local storage, permissions and sharing cautions

- **Offline queue is device-local and encrypted at rest:** command contains gate token, event UUID, timestamp and member/tenant/user IDs (`apps/mobile/lib/offline-check-in.ts:3-6`); the app serializes it into **Expo SecureStore**, not plain AsyncStorage (`apps/mobile/lib/offline-check-in.ts:26-36,74-86`). Expo documents SecureStore as encrypted local key–value storage using encrypted SharedPreferences on Android ([Expo storage guidance](https://docs.expo.dev/develop/user-interface/store-data/)). It is **transmitted off-device when first attempted or replayed**, which transmits token/event/time even if a server error is returned; server-confirmed events leave the queue (`apps/mobile/app/(member)/index.tsx:36-43`; `apps/mobile/lib/offline-check-in.ts:88-117`). Sign-out clears the queue and cached identity (`apps/mobile/lib/native-session.ts:143-148`).
- **Camera:** Android requests `CAMERA` for QR scanning; microphone and external-storage permissions are blocked (`apps/mobile/app.json:12-20,40-55`). Scanner passes QR *text* to the check-in function, not photos/video (`apps/mobile/app/(member)/index.tsx:90-92`).
- **Other SDKs / Google:** With Google sign-in, the user explicitly chooses OAuth in a browser, and Supabase exchanges a PKCE code (`apps/mobile/app/sign-in.tsx:28-29`; `apps/mobile/lib/native-session.ts:91-112`). Google may receive sign-in identifiers and provide name/email/profile to Supabase. **UNCERTAIN:** verify exact Google scopes, data received and any non-exempt onward sharing against live provider configuration; Play's user-initiated-transfer exception is not a blanket exemption for unrelated tracking. Service-provider status depends on contracts/instructions, not just product names. Check embedded SDKs and the final AAB before certifying the form.
- **Do not mark marketing use from the audited app solely because a gym can send messages:** Android reads messages/consent history, but does not set marketing consent or initiate campaigns (`apps/mobile/lib/mobile-data.ts:58-60`; `apps/mobile/app/(member)/gym.tsx:82-88`). If server-side handling or third-party campaigns change, update the declaration.
